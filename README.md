# Project Harness

Project Harness（PH）为 Git 项目提供开发规范、项目资料、需求开发技能和安全升级机制。初始化先核实代码与已有内容，再整理适合项目的约束、架构和测试要求，保留有效正文与用户定制。

本分支正在准备 **1.2.3 自研 SDD**：不再依赖上游 Spec Kit，采用完整需求与简易改动两条流程。正式可用版本以 [Releases](https://github.com/chenweixuanJokes/project-harness/releases) 为准；开发树和本地候选验证不等于已发布。

## 项目目录

```text
.agents/
├── AGENTS.md
├── ph.json
├── skills/
├── scripts/
└── project-harness/
    ├── constitution.md   # 项目原则与约束导航
    ├── constraints/      # 现行规范及冒烟用例
    ├── documents/        # 当前项目事实、架构、使用说明
    ├── specs/            # 稳定需求目录和开发过程
    ├── memory/           # 参考记忆，不是规范或授权
    ├── archive/          # 原件、需求快照与历史资料
    └── runtime/          # PH 自有模板及运行资产
```

业务 `docs/` 仍由项目维护，不作为第二套 PH 目录。根 AGENTS.md、CLAUDE.md 和声明的技能适配入口由所选模式生成；规范源在 `.agents/`。

## 完整需求流程

| Skill | 职责 |
| --- | --- |
| `ph-require` | 明确需求、范围与用户验收目标 |
| `ph-clarify` | 检查并解决需求歧义 |
| `ph-design` | 产品交互和技术实现设计 |
| `ph-design-review` | 对照需求、代码与规则审查设计 |
| `ph-tasks` | 可执行任务，包含必要单元测试 |
| `ph-verify-plan` | 智能体成果自测清单与用户验收指引 |
| `ph-implement` | 执行实现或修复任务及任务内测试 |
| `ph-verify` | 实际自测、用户成果验收、失败回填任务 |
| `ph-archive` | 保存需求历史，沉淀项目文档和可复用用例 |

按表中顺序使用。技能之间只建议下一步，不自动串联。设计审查在任务前，验收准备在实现前；失败由 `ph-verify` 去重追加修复任务，再执行 `ph-implement` 和 `ph-verify`。

**智能体负责证明成果可以正常工作，用户负责判断成果是不是自己需要的。** 单测在 Task 内编写执行，后续自测关注集成、主流程、关键异常和必要回归。智能体自测通过后才交用户体验，不让用户排查日志、检查数据库或重做技术测试。没有用户反馈就记录等待，不宣称验收通过。

## 简易改动流程

局部、明确、低风险的 Bug 或修改用 `ph-small-change` 一次完成必要澄清、最小方案、任务及验收准备，再依次使用 `ph-implement`、`ph-verify`、`ph-archive`。

简易入口只做准备，不立即修改代码。按影响与不确定性判断是否简单，不按代码行数；接口兼容、数据迁移、鉴权或跨模块影响需要完整流程。两条流程共享实现和验证标准，不因文档简短而降低测试要求。

## 并行开发与 worktree

保留两个独立技能：

- `ph-worktree-enter`：明确点名后创建并登记隔离任务工作区，可绑定需求、任务和独占资源。
- `ph-worktree-exit`：明确点名后交付回登记的源工作区，合并前后验证；提交和清理按各自授权规则处理。

`ph-implement` 在已分配工作区中执行，多个独立任务可以并行。共享文件、端口、数据库和外部服务必须分配归属或串行。向同一源工作区的合并串行，单个子任务完成不代表整需求完成，汇总后重新验证。

`ph-archive` 与退出技能互不调用：可以在任务树先归档并明确记录未合入，再独立退出；也可以合入并复验后归档。清理前必须保全证据，不自动删分支或推送。

## 文档与用例沉淀

需求始终保留稳定入口，归档保存快照而不通过搬目录表达状态。归档会对照已实现事实更新受影响项目文档、索引和核验字段。

- 单元、接口自动化测试在实施时写入项目测试目录。
- 已验证且可复用的冒烟场景在归档时登记到对应前后端 PH 用例库，保留编号、来源、脚本、前置、断言、清理和证据。
- 一次性命令和临时环境不是长期规范，未执行用例不能写进通过报告。
- 项目事实、已采纳规则、参考记忆和历史材料分开处理；归档不自动写记忆或把实现选择变成强制规范。

## 安装和升级

需要 Git、Python 3 和支持技能的编码工具。用户级入口目录不存在时可以取得官方入口；目录已有内容则先检查，不覆盖。实际项目安装始终先由入口准备固定正式版本，而不是直接安装开发分支模板。

```bash
git clone https://github.com/chenweixuanJokes/project-harness.git ~/.agents/skills/ph-init
```

在项目中点名：

> 用 ph-init 初始化这个项目，先检查已有代码与文档，确认范围后接入。

> 用 ph-init 升级，保留项目定制，先检查差异。

不要在本分发仓运行 `ph-init init --apply`。普通 check/sync 使用项目已装内核离线执行，不升级。新装 auto 探测相对软链接，不支持时使用 portable；已装项目保留原模式。

1.2.3 升级会识别并保全旧 PH 技能，退役旧活动入口及对应适配副本，安装新技能。同名替换保留归属证据；用户改过的内容或第三方同名项冲突时停止，不能凭技能名覆盖。旧需求、编号、问答、证据和在途 worktree 会话保留。

旧入口可能因硬校验 Spec Kit 契约拒绝新发行包。届时须从**已发布的固定目标标签**在仓外新目录取得新版入口，再完成升级；不改旧验证器绕过，不拿 main 冒充正式版。详见[旧项目升级](docs/从旧版本升级.md)及相邻[迁移说明](migrations/README.md)。

## 技能与语言

新增和本次修订技能以英文 `SKILL.md` 为执行源，`SKILL.zh.md` 为中文对照，不重复注册技能。项目产物默认中文，可按用户语言要求调整。`ph-human` 可检查和刷新产物伴读，伴读不是权威规格或验收证据。

开发、安装、升级、worktree 和记忆写入技能需明确点名；已启动流程继续不要求每轮重复。`ph-memory-ask` 是按回忆意图触发的唯一例外。用户点名 ph-init 请求升级时，可在同会话读取 merge-update 的内部步骤。
