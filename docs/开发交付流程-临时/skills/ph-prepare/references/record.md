# 任务记录

沿用项目工单、意图或已有计划，不新建竞争版本。项目要求的记录和审批优先；只读时使用会话或允许的计划产物，并注明未落盘。

## 小任务

用一段话写清四件事即可，不要求四张表：

- 改什么：当前问题与预期行为。
- 保留什么：既有行为、兼容要求和本次不做的事。
- 怎么改：核实的实现位置、最小改法与必要说明。
- 怎样验证：输入、预期、实际测试入口，以及需要用户判断的结果。

已有事实、权限和路径直接引用，不重复抄写。需要审批时保存真实批准依据；明确修改请求只有在项目允许时才作为实施依据。检查未执行就写待执行，不填示例结果。

## 复杂任务补什么

只补与本任务相关的内容：

- 行为：正常、错误和边界路径，接口、数据、权限及兼容要求。数量指标附测量条件。
- 设计：复用位置、推荐方案、影响选择的备选与取舍，已核实事实和待验证假设分开。
- 任务：一项任务包含一段可验证行为的实现、测试与说明；列对应标准、文件位置、前置依赖、完成判据和停止条件。
- 发布或迁移：顺序、兼容窗口、备份、恢复办法和不可逆步骤。

为持续跟踪的标准和任务保留稳定编号，如 A1、T1。标准写“在什么条件下，执行什么操作，得到什么结果”，不用“体验良好”代替。技术检查和用户反馈分开；内部任务没有用户操作点时说明依据。

## 执行后补结果

每项结果记录对应标准、代码或文件版本、环境、实际命令或操作、结论和证据位置。保存决定性输出，不倾倒全部日志。

未提交内容不能只靠 commit：补充任务文件摘要或快照，包含相关未跟踪文件，排除秘密和无关资料。用户反馈保留原话或忠实转述及日期；模拟反馈明确标记。

阶段状态用未开始、进行中、受阻、完成；检查用通过、失败、阻断、待执行，用户尚未回答用未验收。

## 变更与交接

范围、验收或重要兼容变化时，保留旧决定，记录原因、新决定和受影响任务及检查。取消的标准留下原因，不复用旧编号表达新含义。普通实现细节无需机械重新审批。

交接说明已完成什么、成果在哪里、还有什么阻断、下一步从哪里开始。交付后补实际位置、操作回执和资源保留情况；当前产品说明维护现状，历史任务记录保留当时事实。
