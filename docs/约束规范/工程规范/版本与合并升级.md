# 版本与合并升级

> 本文约束 **Project Harness 分发仓库的维护与发布**。修改 PH 安装/升级行为、Skill、脚手架、Schema 或迁移材料，以及准备提交发行变动、打标签、创建 Release 前，必须先读本文。不要把本文写入下游项目的业务约束。

## 1. 不可省略的发布要求

**每个对外发布的小改动批次都必须递增 `1.1.x` 中的 x，并同时撰写旧版本到新版本的合并升级方案。缺少版本递增或升级方案，不得发布。**

- 一批已关联的改动可以共享一个尚未发布的新版本，不按每次保存文件递增。
- `release.json` 是发布版本及必需 Skill 清单的唯一维护源，不得分别维护互不一致的版本常量。自 `1.1.8` 起彻底取消独立 Schema 版本，只有单一 PH 版本（`1.1.1` 至 `1.1.7` 曾在 `release.json` 与项目清单中同时维护 `schema_version`，属历史布局，最终态以本节为准）。
- 同一版本号下，Skills、运行脚本、规范模板与迁移材料按同一发行身份成套下发、成套验收；项目流程使用项目内成套 Skills，不接入可独立更新的用户级插件。
- 已发布的标签、版本材料和该版迁移说明不可改写。修复已发布内容必须再发一个补丁版本；不强推标签，不把旧标签挪到新提交。
- 正式源只有 `https://github.com/chenweixuanJokes/project-harness.git`。仓库已由 `ph-init` 更名而来：旧地址 `https://github.com/chenweixuanJokes/ph-init.git` 经 GitHub 重定向指向同一仓库，`FIXED_SOURCE`、`release.json.repository`、`receipt.source`、`state.source.repository` 等 1.x 来源标识保留旧地址的兼容含义；**旧名 `ph-init` 不得复用**——不得用它新建仓库或转移给其他项目，否则重定向失效、兼容来源字段指向错误目标。产品对外名称为 Project Harness；安装入口与技能名保持 `ph-init` / `ph-*`，不随仓库名变化。`main` 是开发状态；正式消费采用稳定 `vMAJOR.MINOR.PATCH` 标签，整次操作固定到同一 commit。
- 历史 `1.1.0` 存在多种未打标签的布局，已在迁移说明中补录。以后禁止以相同发布版本分发不同有效内容。

## 2. 哪些变动必须升版本

以下任一发行有效内容变化，必须准备下一版本及迁移说明：

- 根 `SKILL.md`，安装、在线获取、合并升级运行时脚本。
- `assets/scaffold/**`，包括约束模板、Skill、配置、目录与文档默认内容。
- `release.json`、`migrations/**`、随包安装的 evals 等运行材料。
- 文件改名、必需 Skill 增减、模板规则变化，即使没有业务代码变化，也属于发行变化。

仅维护本仓 README、测试、CI、发布校验工具，以及本仓 `.agents/AGENTS.md` 和 `docs/` 维护者规范，且**没有改变任何下游发行有效内容**，可以作为维护性修改保留当前版本。不得用这个例外掩盖模板/Skill/运行时变化。只要对外发布新的 PH 行为批次，仍需新版本。

Schema 版本已随 `1.1.8` 彻底取消（历史上 `1.1.1` 至 `1.1.7` 曾与发布版本分开维护、始终保持 `1.1.1`，那段描述仅作历史记录）。现在结构或校验契约变化随 PH 版本一起发布，并在该版迁移说明中写清，不另立版本号：发行包与项目清单都不再有 `schema_version` 键，`ph.schema.json` 的 `$id` 固定为无版本的 `urn:ph:schema:project-harness`，不另升编号。下游 `.agents/ph.json.template_version` 表示项目**已完成适配**的版本，不是下载到的更新包版本；`format_version` 等内部格式标识不受本变化影响。

## 3. 每个新版本的交付清单

准备新版本 `<new>` 时，必须同时完成：

1. 核对远端已发布稳定标签，确认前一正式版本 `<old>`，不能仅凭过期本地副本猜起点。
2. 更新 `release.json.version`，同步 scaffold manifest 的 `template_version` 和相关版本声明；`ph.schema.json` 的 `$id` 固定为无版本 `urn:ph:schema:project-harness`，结构契约变化随本批迁移说明写清，不另立版本号。
3. 新增 `migrations/<old>-to-<new>.md`，并在 `migrations/index.json` 登记相邻版本、文档路径、顺序及唯一迁移项 ID。历史链必须完整，不覆盖旧说明。
4. 更新 `CHANGELOG.md`；区别“变化摘要”和“存量项目如何合并”，摘要不能代替升级方案。
5. 补充回归与 Skill 行为样例；确认旧入口可获取新版本、旧项目无需先覆盖自身才能启动升级，并按第 6 节历史升级矩阵验证所有历史状态到 `<new>`。
6. 完成下节验收，再提交发行变动、打对应标签和创建 Release。提交应能清楚看出版本与迁移说明一起交付。

## 4. 合并升级方案必须回答什么

格式与完整模板见 [迁移说明维护规则](../../../migrations/README.md)。每次至少写清：

- **why / from / to**：为什么变、支持哪些旧状态、新状态是什么。
- **affected**：影响的文件、目录、Skill、字段与当前有效引用；按迁移项描述具体操作及必要顺序。
- **preserve**：哪些项目定制、业务正文、历史原话、编号和兼容目录必须保留。
- **conflict**：哪些情况 Agent 不能自行裁决；如何记录阻断，不覆盖冲突内容。
- **verify**：用哪些命令、结构检查及内容证据证明适配完成；部分执行与重试如何恢复。

即使无需修改存量文档，也必须写明“无需存量文档迁移”及理由和验收方式，不能省略迁移记录。跨多个版本时读取整个相关链，可合并已被后续版本取代的中间操作，但不可漏掉必要迁移。

## 5. 项目升级边界

- 用户入口只有 `ph-init`。`init` 负责首次安装；普通 `sync` 仅同步适配层；已装旧版由同一会话按 `ph-merge-update` 步骤读取迁移链并驱动 Agent 语义合并。禁止重跑 `init --apply` 强盖旧项目，也不要求用户另开技能；用户级 `ph-init` 仅是安装与升级入口，入口自身更新不代表项目升级。
- 先获取正式版本，固定 tag/commit；网络失败或迁移链缺失时停止，不拿本地旧模板或开发分支冒充最新。
- 旧版（`1.1.7` 及更早）入口的 prepare 必查发行元数据里的 `schema_version`，会**必然拒绝** `1.1.8` 及以后的包。这不是可自动恢复的故障：升到 1.1.8 走一次性入口切换——从官方稳定标签 v1.1.8 clone 到一个**新的仓外安全目录**（如 `mktemp -d`），不覆盖用户级入口与目标项目，不用 `main` 或本地开发树冒充发行；从该新目录运行 `ph_release.py prepare --version 1.1.8`，读取返回发行根的 `SKILL.md` 继续。标签未发布前不实际执行该下载。
- 合并阶段先更新无版本 `$id` 的配置校验文件与自包含运行脚本，verify 前须已符合目标包。磁盘清单中的旧 `schema_version` 和 `template_version` 保持原值，直到 finalize 的候选检查通过后才删除旧字段并写新版本（此口径针对 1.1.x 旧 schema 清单；1.2.1 起清单校验器固定 `template_version` 等于目标版本，re-key 即写新值）；随后常规 check 通过才标记完成。
- 项目配置、已填写约束、Wiki、意图和访谈不是可任意覆盖的模板。只改迁移要求的内容，保留 adapter mode 和项目事实。
- 项目 `.agents/updates/<new>/state.json` 与 `report.md` 记录真实处理结果、来源和验证证据。只有全部必需项完成、候选检查及适配层验证通过，才能 finalize 推进项目版本并标记 complete。即使合并阶段已按目标清单写入 `template_version`，也只有成套合并验收通过才能认定项目升级完成；版本字段不能替代验收证据。项目定制按迁移要求保留，不强制与模板字节一致。
- 中断后依据磁盘实态和记录恢复，不重复插入内容，不因版本字段已写入就跳过未完成验收。
- 同步本地多个副本时先盘点真实作用域，排除 trash、临时测试、历史备份与内嵌 scaffold；保护未提交改动。非 Git 模板只能如实记录隔离副本验收与回写复核，不假称原目录执行过 Git 仓库验收。

## 6. 发布门禁

在仓库根执行并确认通过：

```bash
python3 scripts/check_release.py
python3 -m unittest discover -s tests -v
```

准备正式标签后，还必须执行：

```text
python3 scripts/check_release.py --tag v<new>
```

发布前确认版本递增、迁移链完整、元数据/模板/Skill 一致、旧项目定制保留、重复执行和失败不误升版本。发布后确认 CI 通过，再从公开固定源匿名获取该标签，验证新项目安装及受支持旧项目升级；本地 fixture 通过不能代替公网分发验收。

失败必须如实报告，不跳过门禁，不因为赶发布而强制覆盖或改写已发布标签。提交、推送、发布仍需当前用户授权；本文不是自动发布授权。

### 历史升级矩阵（必过标准）

任何安装、升级、迁移及其发行有效内容的改动，都必须先通过历史升级矩阵，证明所有历史状态都能升级到当前最新版；发行/迁移相关修改必须跑历史矩阵、完整 unittest 和 `check_release.py`，失败不得验收。矩阵测试（`tests/test_historical_upgrade_matrix.py`）随上文完整 unittest 一起执行，规则如下：

- 历史范围以 `migrations/index.json` 为准，每个旧版本都要覆盖；无 tag 的已知历史状态使用固定 commit 构造，当前包括 `1.0.0`、两套 `1.1.0` 布局与 `1.1.2`；两套 `1.1.0` 布局（旧命名 / 新命名）分别覆盖；portable 与 symlink 两种 adapter 模式都覆盖。
- 用历史版本自身的安装工具在隔离仓库构造真实旧项目，不得只改最新版 manifest 的版本号模拟旧状态。
- 每条迁移项都有明确适配与证据；新增迁移项或新版本必须自动进入矩阵，矩阵缺该历史状态支持即失败，不准 skip。
- 验证至少覆盖项目定制保留、冲突与失败不误升版本、中断恢复、finalize 幂等。
- 本地脚本矩阵只证明脚本链路，Agent 语义合并与公网分发验收不能被它冒充，也不能拿 fixture 通过冒充公网分发验收；发布前的真实项目实测按 [本地E2E测试](./本地E2E测试.md) 执行（临时副本三案例，覆盖两种适配模式）。

本小节只约束本仓维护者，不进入下游 scaffold，也不改写已发布迁移材料。按第 2 节例外，仅涉及本仓文档、测试、CI 的维护性修改（含本小节自身与配套矩阵测试）不升版本。

## 7. 本仓约束入口与分发边界

本仓仅以 `.agents/AGENTS.md` 为完整约束源；根 `AGENTS.md`、`CLAUDE.md` 是直接相对软链接，引用本源，不复制正文。根入口属于本机维护适配，不进入正式发行文件清单：当前在线获取器会拒绝发布树中的软链接，不能为了附带维护入口破坏旧版在线升级能力。

本仓维护者文档不放入 `assets/scaffold`，也不加入 `ph_init_payload_files()`；下游需要更新的规则必须单独修改对应 scaffold，并按上述规则发布新版本和迁移说明。
