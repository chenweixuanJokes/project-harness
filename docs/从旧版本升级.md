# 从旧版本升级

官方仓库由 ph-init 更名为 project-harness，旧地址重定向保留。技能入口名与用户级路径仍是 ph-init，1.x 来源字段中的旧 URL 保持兼容，不手工改写。

## 日常升级入口

在项目中明确点名：

> 用 ph-init 升级 PH，保留项目自己的规则、技能定制和历史需求，先检查差异。

入口先准备固定正式版本，再读取迁移链、保全旧内容、合并和验收。不能在旧项目运行 init --apply 强盖，也不能用 git pull 目标业务仓代替升级。

## 1.2.3 自研 SDD 过渡

本分支正在准备 1.2.3，**是否可安装以官方稳定标签实际存在为准**。旧入口对 schema_version、必需技能名单或 Spec Kit 元数据有硬校验，可能拒绝新包；这是入口契约变化，不是通过反复重试可解决的网络故障。

正式标签发布后，使用该标签自身的新工具完成一次性入口切换：

1. 核实官方 v1.2.3 标签和 commit，在项目之外取得新的安全目录，不覆盖旧用户入口或目标项目。
2. 在该固定标签目录运行 `python3 <新目录>/scripts/ph_release.py prepare --version 1.2.3 --repo <目标项目>`。
3. 读取返回发行根的 SKILL.md，使用该根的迁移工具检查并升级，整次操作固定来源。
4. 准备根可按规则刷新已存在的旧用户入口；入口刷新和项目升级分别报告结果。

标签未发布时不执行上述公网安装，不拿 main 或本地候选冒充发行版。更早的 schema/技能拆分过渡保留在对应历史迁移说明，读取完整链处理，不改旧标签或旧验证器绕过检查。

## 升级保留什么

- 项目原有 portable/symlink 模式及有效规则、资料、测试和记忆。
- 旧 spec.md、plan.md、任务编号、问答、附件、验收证据和伴读。
- 在途 worktree 会话、任务分支及证据。
- 旧技能完整原件及迁移处置证据。

新发行会清理可证明受管的旧开发技能和厂商入口，再安装自研技能；同名 clarify/tasks/implement 是受控替换。用户修改或第三方同名不能凭名称直接覆盖，冲突项保留并阻断。旧产物接续不把历史完成勾选自动变成当前用户验收通过。

升级脚本通过只证明结构检查，旧内容是否有效承接还需语义审阅。中断从同批记录恢复，失败不能报告项目已升级完成。

## 更名与手动克隆

仓库更名本身不要求迁移技能路径或重装。不要在旧名 ph-init 下创建其他仓库，避免切断重定向。若手动调整本机 clone 的 remote，应先核实目标仓库；这不代替业务项目升级。

具体相邻版本步骤见[迁移说明](../migrations/README.md)，本地维护与发布门禁见[版本与合并升级](约束规范/工程规范/版本与合并升级.md)。
