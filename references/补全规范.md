## 1. 完成标准

一次文档补全交付必须同时满足：

1. 只读盘点已覆盖模块、代码、配置、真实依赖（锁文件）、测试、CI 与既有约束 / Wiki / AGENTS，并写明缺口；旧文档目录已按 [接入规范](接入规范.md) §1.1 处理。
2. 实际在用的栈已按 [接入规范](接入规范.md) 第 3 节留下官方资料记录；离线或查不到的标 `待核实`，不编造版本。
3. 存量正文未被模板覆盖：将被改动的原文已先备份到 `project-harness/archive/legacy-backup/`；合并经仓外候选与 `sources` 哈希快照完成，已有正文以 `复用` 登记引用，冲突未擅自裁决。
4. 矩阵中适用条目都有落点：已填真实值、登记 `复用`、标明 `不适用`，或因冲突停止并留下续做说明。
5. `.agents/init-report.md` 按第 4 节覆盖矩阵全部独立 id，结果如实，未编造项目记录。
6. Wiki 非模板页的五个字段均为真实值：`owner` / `status` / `last_verified` / `verified_against` / `refresh_trigger`（填写规则见 [文档治理规范](../assets/scaffold/.agents/project-harness/constraints/harness规范/文档治理规范.md) 第 4 节）。owner 未知写 `unknown`，不猜人名。
7. 写入的命令若只是从脚本 / README / CI **静态抄出、本轮未执行**，必须标明 `未执行，待核实`。
8. 沿途索引与相对链接仍指向真实存在的文件：`documents/` 各级 README 由主会话汇总，`constraints/` 宪法导航由 PH init / 升级刷新，不出现双写分叉。
9. 失败或中断时：已验收段落保留，未完成项可续做，不因部分成功宣称全部完成。

未完成补全前，不得把占位符、空表或过期叙述当成现行答案。

## 2. 分阶段与文件归属

安装完成后按文件归属拆 subagent；同一文件只允许一个写入者。建议阶段：

1. **栈盘点**（只读，主会话或一个检索 agent）：产出七类证据表、有无前端 / 后端、CI 入口、现有定制与旧目录清单。
2. **官方资料**（可按组件并行，只读）：回传 [接入规范](接入规范.md) 第 3 节记录，不写项目文档。
3. **写入**（按独立文件并行）：
   - Wiki：`项目概述.md`、`功能地图.md`、`开发指南.md`、领域页、架构三页。
   - 各端：`前端规范/` 与 `后端规范/` 各专文（技术规范、样式 / 数据规范、自测规范、构建规范）。
   - 工程与测试：[Git规范.md](../assets/scaffold/.agents/project-harness/constraints/工程规范/Git规范.md)、[安全规范.md](../assets/scaffold/.agents/project-harness/constraints/工程规范/安全规范.md) 与 `测试规范/` 各专文。
4. **共享索引 / 入口**：由**主会话**统一更新本轮受影响的 `documents/` 各级 README 与宪法导航（`constraints/` 不设目录 README，导航由 PH init / 升级刷新），以及 `.agents/AGENTS.md` 的一句话与技术栈。subagent 只回传所需索引变更，不抢写共享文件。改 canonical 后按原 mode 同步适配层并重新 check。
5. **覆盖报告**：主会话汇总 subagent 回传的结论行，统一维护 `.agents/init-report.md`（第 4 节）。

失败时保留已验收文件，下轮从盘点结论续做，不重写已核验段落。范围扩展或与原有定制冲突：停止**受影响项**，其它无关文件可继续。

- 旧正文之间或旧正文与当前实态矛盾时记 `冲突`，双方证据都留，交用户裁决。
- 每个条目的处理结果落入第 4 节覆盖报告；报告未覆盖的条目视为未处理。

## 4. 覆盖报告：`.agents/init-report.md`

初始化补全的**实现记录**：记录做了什么、证据在哪、结果如何。它不是业务意图、不是规范正文、不进 `docs/` 三域，也不因它自动生成意图 / 记忆 / ADR。

形式为表格，每个矩阵条目至少一行，列至少五项：

| 列 | 要求 |
| --- | --- |
| `id` | 第 3 节稳定条目 id；同落点多 id 可合并一行，但不得漏 id |
| `落点` | 最终写入或引用的文件（含章节），或 `不适用` 的说明位置 |
| `仓内证据` | 支撑结论的具体位置：路径、命令、锁文件条目、CI 文件、旧规范条目 |
| `结果` | 枚举五选一：`已核验` / `复用` / `不适用` / `待核实` / `冲突` |
| `说明` | 一句话：核实了什么、缺口是什么、为何冲突 |

结果语义：

- `已核验`：本轮对照仓内证据核实过。
- `复用`：已有正文被引用或登记，未重写。
- `不适用`：无该端 / 组件 / 流程，写明依据。
- `待核实`：证据缺失或来源不可达，写明缺口。
- `冲突`：与旧正文 / 代码 / 模板矛盾，留双方证据，待用户裁决。

覆盖范围：**第 3 节每个独立 id 至少一行**（E1–E2、C61–C65、F3–F34、D35–D39、D40–D44、C45–C50、D51–D60）。PH 通用流程条目（采用既有 Skill 或文档流程的，如 C62 / C63、D51–D57、D58–D60、C50）写**采用声明**即可：结果按实际情况记，不为它们编造项目执行记录。

维护：subagent 回传结论行，**主会话**统一写入与更新，避免双写。补全中断时保留已完成行；续做从报告与磁盘实态恢复，不重跑安装。

同一条目仍有实质缺口或冲突时，`结果` 必须标 `待核实` 或 `冲突`，不能只在页脚登记问题却把矩阵标成全部已核验。全量覆盖表示每个条目均有交代，不表示问题全部解决。代码可纠正当前实现的事实摘要，但与既有强制规则冲突时，只记录差异，不以“代码为准”擅自废止规则。

## 5. 补全禁令

- 不为 F / D / C 每个叶子建空 `.md`。
- 不把 `待采纳建议` 写进「必须 / 禁止」句式。
- 不把记忆或意图当初始化产物批量生成。
- 不把 PH check、单测偶发通过或模型总结写成 `last_verified` 证据。
- 不把 init-report 写进 `docs/` 三域或意图目录；不在报告里把建议、未执行命令、未核实条目记成 `已核验`。
- 相对链接指向最终交付中真实存在的文件。已有专文优先；在已授权范围内，有足够事实时可按单一主题拆专文：文首写「使用时机：」，并经 PH init / 升级刷新宪法导航与受影响索引。
- 超出本次用户授权范围或与原有定制冲突时，停止受影响项并报告；不为补全文档顺手改业务代码、部署或创建过程记录。
