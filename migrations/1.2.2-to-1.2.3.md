# 1.2.2 → 1.2.3

## why

1.1.14 起的十个规格驱动技能（ph-analyze、ph-checklist、ph-clarify、ph-constitution、ph-converge、ph-implement、ph-plan、ph-specify、ph-tasks、ph-taskstoissues）始终由上游 GitHub Spec Kit 固定版本经 `ph_speckit.py` 安装与刷新：发行依赖上游 tag+commit 锚点与随包哈希清单，技能正文是上游生成物的改写，产物命名（spec/plan/tasks）与上游模板绑定，宪法物化与导航校验寄生在安装器里。本批把规格流程彻底收归自研：发行树不再携带 `speckit.json`、`assets/speckit-bundle.json` 与 `scripts/ph_speckit.py`，必需 Skill 唯一来源固定为 18 个自研技能（8 个既有 PH 技能 + 10 个新规格技能），产物改为 requirement/design/review/tasks/verify-plan/acceptance/verification（small 流程以 change.md 合并需求与设计审查），宪法物化与导航校验提取为独立的 `scripts/ph_governance.py` 由 init / 升级直接调用。

### 旧入口一次性过渡（必读）

1.1.14 至 1.2.2 的用户级入口 `prepare` 1.2.3 包会**硬校验失败**：该时期校验器要求上游技能集合与 `speckit` 契约，新包不再提供，prepare 报错且不会写成功回执。1.1.1 至 1.1.7 的下载入口还会因独立 schema 版本契约拒绝，1.1.1 之前没有在线下载入口；1.1.8 至 1.1.13 的入口经历史矩阵验证可以直接接受新名单，不能把所有旧版一概判断为失败。这不是可自动恢复的故障。升级 1.2.2 项目走一次性入口切换：从官方稳定标签 `v1.2.3` clone 到一个**新的仓外安全目录**（如 `mktemp -d`），不覆盖用户级入口与目标项目，不用 `main` 或本地开发树冒充发行；从该新目录运行 `ph_release.py prepare --version 1.2.3`，读取返回发行根的 `SKILL.md` 继续。标签未发布前不实际执行该下载。不为兼容保留上游运行。

## from

1.2.2 的 8 个 PH 技能 + 10 个随包规格技能、`speckit.files` 逐文件内容基准、`.agents/project-harness/runtime/` 内的 Spec Kit bash 运行时与模板。更早版本按完整迁移链升级，不跳过历史迁移项。

## to

### `sdd-skill-replacement`

自研技能替换，由发行根 `ph_merge_update.py migrate-skills --repo <项目> [--apply]` 确定性执行（先 plan 后 apply；全体目标预检无冲突才落笔；每步幂等，中断后重跑续做）。新目录先写入 `.agents/updates/<目标版本>/sdd-skill-staging/` 中本次唯一暂存目录，核对发行字节后原子就位；中断残留和未知暂存内容原样保留，重试用新暂存，不凭路径名称接管他人内容：

- **退役 7 个旧技能**：ph-analyze、ph-checklist、ph-converge、ph-constitution、ph-plan、ph-specify、ph-taskstoissues 整目录（含 evals、references 与用户附加文件）逐字节归档到 `.agents/project-harness/archive/legacy-backup/<日期>-pre-update/retired-skills/<名>/`，证据逐项列出非受管附加文件，可随时找回。
- **原位替换 3 个同名技能**：ph-clarify、ph-tasks、ph-implement 换为自研新契约；旧目录同上整目录归档后从发行根 scaffold 安装新目录。
- **安装 7 个新技能**：ph-require、ph-design、ph-design-review、ph-verify-plan、ph-small-change、ph-verify、ph-archive 从发行根 scaffold 全新安装。
- **同名身份识别**（以 SKILL.md 为锚）：磁盘 SKILL.md 与发行根 scaffold 字节一致时识别为新代，仍逐文件核对目标文件；缺件可补齐，已存在但不同的正文、中文对照、references 或 evals 不可无依据覆盖。SKILL.md sha256 与 `.agents/ph.json` `speckit.files` 记录的安装基准一致时识别为受管旧代，整目录保全后换新；两者都不符时按用户定制或第三方内容阻断、原位保留。基准只证明所记录的文件，不能据此丢弃附属资源。manifest 无任何基准且无法证明同名目录为当前发行时阻断；新增技能路径的未知同名内容也不能静默跳过。
- **附属文件语义处置**：受管旧代目录里出现已知受管集（SKILL.md、evals/evals.json）之外的文件时，迁移无法判定其是否仍是有效定制，不会仅凭归档宣称"已迁移"——整项先阻断并列出文件清单；确认处置后用 `--extras-decisions <JSON>`（按技能给 `{"decision": "archive", "note": "<审阅结论>"}`）放行，决定与文件清单逐条写入归档旁 `<名>.extras.json`（ph.retired-skill-extras/1）留证，可审计、可找回；不提供决定即保持原位不动。
- **厂商镜像退役**：`.claude/skills/<名>` 镜像先于本体处理——portable 镜像与受管本体逐字节一致才随本体归档，不一致视为用户内容阻断；symlink 镜像先把确定性记录写进归档再摘链（沿用 1.1.9 codex 退役模式），中断可凭记录续做。新技能镜像由 finalize 的适配层同步创建。
- `.agents/ph.json` 的 `skills.required_names` 更新为 18 个自研技能，旧 `speckit` 节及基准先在原件/迁移记录中保全，技能识别和退役使用该原始证据；切换目标清单契约时删除该节并写目标格式。即使 re-key 已写 `template_version=1.2.3`，仍须全部迁移项、内容验收及 finalize 通过才算升级完成，不用版本字段代替验收。

### `sdd-runtime-takeover`

自研运行时接管：

- 发行根退役 `speckit.json`、`assets/speckit-bundle.json`、`scripts/ph_speckit.py`（本仓退役文件移入系统废纸篓，不入发行）。
- 项目内 `.agents/project-harness/runtime/` 中的 Spec Kit bash 脚本、旧模板（spec/plan/tasks/checklist/constitution/verification）、`SPEC-KIT-LICENSE`、`init-options.json`、`integration.json`、`.constitution-template.json`、`templates/overrides/constitution-template.md` 与 `runtime/.gitignore` 由新自研运行时替换（运行时仅保留 README 与 `templates/sdd/` 八模板）；被替换的旧文件先归档到 `archive/legacy-backup/<日期>-pre-update/retired-runtime/` 再落新文件。保留 `runtime/feature.json` 原指针供历史兼容读取，不再用它定位并行需求的唯一活动目录；`project-harness/specs/` 根及旧功能路径保持稳定。
- 宪法物化 / 导航刷新 / 内容证据校验提取为 `scripts/ph_governance.py`（随 ph-init 载荷自安装分发）：`materialize-constitution` 仅在缺失时创建 `project-harness/constitution.md`，已有宪法是用户内容永不覆盖；`refresh-navigation --expected-sha <已审阅sha> [--apply]` 只替换标记区内导航条目（兼容识别 1.2.3 前旧标记），原则正文逐字节不动；`verify-content` 校验约束终态与证据报告；`verify` 校验导航逐篇覆盖 constraints、使用时机非空、无上游占位符。升级会话在受影响约束文档合并后按审阅哈希执行一次导航刷新。
- 旧受管技能刷新：本批修改的 ph-init 载荷、ph-merge-update、ph-worktree-enter、ph-worktree-exit、ph-human 按既有受管合并规则更新，项目定制保留。
- `ph_init.py` 的 CLI 入口禁用自身导入产生的字节码缓存，正常 check 不再向安装载荷写入 `__pycache__`；不要求用户靠环境变量维持只读。
- 发行准备取消附带账户操作：新版 `ph_release.py prepare` 默认只获取并验证固定发行包，不点星、不创建 fork。独立 `support` 命令只供用户明确授权后调用；升级本身不是该授权。历史入口测试隔离旧 support hook，不使用真实账户重现旧默认行为。

## conflict

以下情况相关写入停止、逐项报告、不降级为静默跳过：同名技能目录字节与发行根新代及 `speckit.files` 基准都不符（用户定制或第三方内容）；受管旧代目录含未知归属附属文件且未提供 `--extras-decisions` 审阅决定；`.claude/skills/<名>` 镜像与受管本体不一致；归档目标同名冲突（双方保留、人工裁决）；宪法被改动后按旧哈希请求刷新；受影响文档存在识别不了的定制冲突；`.worktrees/` 内出现异常占用。禁止 `rm`；退役统一进归档或系统废纸篓。1.2.2 旧入口 prepare 新包必然硬失败，属预期一次性过渡，不重试、不降级换源。
