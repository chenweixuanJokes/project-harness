# 1.1.13 → 1.1.14

## why

1.1.13 及更早的 worktree 流程把未提交改动分成两套不一致的处理：进入时源工作区脏一律停止、把清单交用户自行处理；退出提交却按 staged / unstaged 分级默认普通提交，只有分级无法判定（两者并存或含 untracked）时才停下来开放式问"这次提交要包括哪些"。实际执行中出现三类问题——同一处脏工作区在进入与退出被区别对待，用户不知道下一步该做什么；开放式问句没有固定选项，回答无法直接对应一个可执行决定；更严重的是，"用 ph-worktree-exit 收口"容易被当成对 `wip:` 提交本身的授权，分级默认提交可能在用户只看了摘要、没确认范围时就把混合改动收进一个提交。本版统一为"WIP 统一确认"：凡因未提交改动实际阻断的 worktree 操作，都先展示目录、分支、完整清单与拟用提交信息，再实际调用问答工具提出固定问句、只给两个固定选择；问句问的是"是否采用 `wip:` 提交解决当前这次阻断"，不是对文件内容的逐项审批；未确认一律停止。同时，受确认的提交不再由 Agent 手写拼装，而由运行时脚本统一的 `wip` 子命令执行（dry-run 只读，确认后显式 `--apply`）；脚本不能也不需要证明真实用户确认，人类确认永远发生在调用之前。

同时，1.1.13 的合并冲突恢复只有一行"继续用 continue，放弃用 abort-merge"，放弃时问的是开放式问句"你是自己改完后继续合回，还是放弃这次合回"，没有固定选项；何时可以 continue、abort 的授权边界、冲突现场与 WIP 的关系都没有约定，实际执行中出现用户口头说"改好了"就被当作继续授权、冲突条目被想当然收进提交、Agent 自行代改冲突文件等情况。本版把冲突恢复并入统一确认机制：先只读确认真实冲突态（存在 `MERGE_HEAD` 与未合并条目）并列明冲突清单，再实际调用问答工具提出固定冲突问句，只给"保留现场，我解决后继续""撤销这次合并"两个固定选择；继续须用户明确"已解决并暂存，请继续"并只读核验，撤销由该选项本身授权且仅本次。本版同时给运行时补齐恢复与校验能力：`continue` 与 `abort-merge` 执行前依据 session 合并快照核对 merge 身份，旧 session 缺新增证据时保守阻断，用只读 `doctor` 诊断、显式 `recover` 恢复，不猜测、不声称能恢复所有旧 merge。

同时，1.1.13 新增的 `ph-intent-verify` 在真实验收中暴露出执行语义的缺口：入口一节只区分网页与非网页，没有规定按意图实际目标用户选择正式入口，也没有处理远端 localhost、无入口功能与辅助工具的边界；验收点的粒度、多端多角色覆盖、异步与文件类标准的观察方式、深链对导航权限标准的绕过都没有约定；用户反馈四态与代理预检证据容易混写，矛盾时可能直接记通过或替用户编造不通过；「记录」要求的事项不含入口、角色与已知构建；只读模式的"不写"没有禁止准备写操作，非只读时的写入范围也未限定为只追加目标意图记录。独立实际验证还发现预检缺口：代理曾向本机 localhost 端口发请求并把无关项目服务返回的 401 当成被验收接口的证据——端口可连通不等于服务归属本项目。本版以迁移项 `intent-verify-acceptance-contract` 把这些执行语义写清（含发请求前核实目标服务归属），调用门禁不变。

此外，任务收尾缺少一个只核实事实的核查技能：一轮工作做完后，"改好了吗、测试了吗、合并了吗、还有无遗漏尾巴"四问常被之前的口头宣称或会话总结带过——没有测试证据也算"测过了"，工作区干净被当成"已合并"，目标分支靠猜，待办授权被一句"都弄好了"掩盖。本版以迁移项 `sure-skill` 新增第十三个必需 Skill `ph-sure`：收尾时逐项以当前磁盘、命令与版本控制的真实证据取证，逐项结论只有已证实、未证实、不适用（测试另分未测试与失败）；分支无未提交改动不等于已合并，目标分支不明确就问用户；核查本身不构成新的提交、合并、推送、发布、删除授权，也不越过用户验收门禁。

## to

PH 1.1.14：必需 Skill 从十二个增至十三个（新增 `ph-sure`）；worktree 运行时脚本（两个 `ph_worktree.py`）随 `worktree-wip-confirm` 项同步扩展。三项迁移：

### `worktree-wip-confirm`

- **统一 WIP 确认**，同一套规则适用于三个位置：`ph-worktree-enter` 的源工作区（创建被脏状态阻断时）、`ph-worktree-exit` 的任务树（交付前有 staged、unstaged 或 untracked 内容时，不再按分级默认普通提交）、`ph-worktree-exit` 的合并目标源工作区（合并被脏状态阻断时，`wip:` 提交做在源工作区）。流程：先只读检查，列明所在目录、当前分支、staged / unstaged / untracked 完整清单与拟用的 `wip: <说明>` 提交信息，用于说明现场与安全筛查结果；随后按 `Git与并行开发.md` 第 2 节的**固定问句模板**（只替换目录、分支、清单、wip 说明、后续动作五个变量）**实际调用问答工具**提问，问答工具的两个选项文案固定为"确认 WIP 并继续""停止，保留现场"，不添加其他预设选项，也不禁用宿主自带的自由输入（自由输入按其本意处理：同意才提交）；没有可用问答工具或工具故障时，按《对用户提问》的降级规则用可见文字提出同一模板并等待回答。不开放式问"怎么办 / 要包括哪些"。WIP 确认问的是是否采用 `wip:` 提交解决当前这次阻断，不是对文件内容的逐项审批。
- **授权与停止语义**：用户确认后才执行这次 `wip:` 提交；拒绝、取消或未回答时保留全部改动并停止创建 / 暂停交付，不 stash、不丢弃、不改用其他提交方式、不换问法重问。确认后到这次提交实际执行前，同一阻断场景内的普通内容变化不需要重新确认，也不与提问时的清单逐字绑定；授权不是长期授权：该提交一经执行授权即消费，该阻断场景结束后再次被未提交改动阻断（包括后续步骤、下一次交付或该工作区再次变脏），按当时的现场重新确认。WIP 确认只覆盖这次 `wip:` 提交，不授权普通提交、清理或任何安全检查豁免；`ph-worktree-exit` 开头的授权句已改写——调用本技能表示用户授权完成必要的验证与合并，任务树提交（无论 WIP 还是正式提交）必须按"提交范围"单独取得确认，调用本技能本身不构成任何提交确认。用户已在本次会话单独明确指定的正式提交（范围与消息齐备）仍按指定执行，不擅自改成 WIP。
- **统一脚本与运行时扩展**：受确认的 `wip:` 提交由运行时脚本统一执行，不由 Agent 手写 `git add` / `git commit` 拼装：`wip --repo <工作区> --message "wip: <说明>"` 只读 dry-run 审查计划，用户已确认后显式加 `--apply` 执行；提交把 staged、unstaged、untracked 一起收进，ignored 排除，不盲目 `git add -A`；受确认提交完成后脚本只见 clean 工作区。脚本自身不向用户征求授权，脚本无能力证明真实用户确认，其安全分级只在 `--apply` 时兜底拦截其不接受的状态，人类确认由 Skill 流程在调用 `--apply` 前完成。运行时同步扩展：`exit` 不再接收提交信息（兼容接受旧 `--message` 参数但绝不据此提交），任务树提交一律由受确认的 `wip:` 或用户单独指定的正式提交完成；`enter` 新增 `--expect-source-head` / `--expect-source-branch` 显式校验期望源，与实际不符时停止；新增只读诊断 `doctor`（无 `--apply`，不做修复）、显式恢复 `recover`（`--session <session JSON 路径> --action archive|adopt`，目标与操作由用户显式指定：archive 仅适用于隔离目录已清理或目录不存在且未登记的残留记录，adopt 仅适用于 creating 记录且现存登记 worktree、分支与 initialTaskHead 吻合）与重新交付 `redeliver`（仅适用于 session 处于 `committed` 或 `merge_verify_failed` 且任务分支在其后出现新提交，先核验再交付）；session 合并快照新增 `mergeSourceBranch` / `mergeSourceHead` / `mergeTaskHead` 字段，新增字段非必填、旧 session 只读兼容，迁移不覆盖现有 session。
- **安全筛查保持**：WIP 提交只收进通过安全筛查的路径；疑似密钥文件或内容、异常大文件、ignored 文件与未解决的冲突不得为 WIP 或任何提交收进，也不得绕过安全门禁，须如实列为剩余阻断由用户处置。存在无法纳入的非 ignored 变动时，创建 / 交付在其被用户处置之前保持阻断：脚本对这类状态整单拒绝、不部分提交，即使其中部分路径已另行经授权提交，也不得把该工作区当作干净继续操作或调用 `--apply`。禁止 `git stash`、`--no-verify`、`reset --hard` 的既有约束不变。
- **冲突恢复固定问句**：`ph-worktree-exit` 遇合并冲突保留 Git 标准 merge 状态，先只读确认存在 `MERGE_HEAD` 与未合并条目并列明冲突清单、依据 session 合并快照核对 merge 身份，再按 `Git与并行开发.md` 第 4 节的固定冲突问句模板实际调用问答工具提问（只替换目录、任务分支、源分支、清单四个变量），两个选项固定为"保留现场，我解决后继续""撤销这次合并"，不添加 stash、丢弃、一键选 ours/theirs、Agent 代解决等其他预设选项，也不禁用宿主自带的自由输入。保留现场即停止等待，不立即 continue、不轮询；用户明确说"已解决并暂存，请继续"时只读核验无未合并条目、核对 merge 身份、session 与任务分支未变、merge 状态吻合，才执行 `continue --apply`，既有具体授权不重问；仅文件无冲突标记、或口头说已解决而没有明确要求继续，都不是继续授权。"撤销这次合并"是仅本次 `abort-merge --apply` 的单独授权，执行前说明冲突解决的编辑会被撤销并只读核对 merge 身份，不自动重试 exit、不删除任务分支或隔离目录。取消、跳过或未回答同样停止：不 abort、不做 WIP、不换问法重问。用户明确委托 Agent 解决冲突属单独授权，不能从退出技能、WIP 或保留现场选项推导；冲突条目涉及业务取舍仍停止交用户。新一次 merge 冲突重新提问，不复用旧授权。现场与 session 登记不符（陌生 merge）或旧版本创建的 session 缺少新增证据、无法核对 merge 身份时保守阻断，不猜测补齐：先 `doctor` 只读诊断，确需恢复登记由用户显式指定目标与操作（`recover`），recover 不能恢复所有旧 merge，诊断与恢复之外的状态交用户处置。
- **冲突态优先于 WIP 流程**：合并前源工作区或任务树的脏改动按统一 WIP 确认处理；merge 已发生冲突后，未合并条目不得转成 WIP 或任何提交收进，冲突全部解决并暂存后由 `continue` 生成的合并提交不是 WIP 提交，清理隔离目录仍另行确认。
- **规则索引与样例同步**：`Git与并行开发.md` 的"WIP 不得静默执行"与退出提交两段改写为统一确认口径，并新增固定问句模板节；异常处理表合并冲突行与新增冲突固定问句段同步冲突恢复口径；`.agents/AGENTS.md` 并行开发规则中"进入 worktree 前遇到未提交改动必须停止"一条改写为统一 WIP 确认口径，并新增合并冲突恢复条目；两个 worktree Skill 的 `evals/evals.json` 合并统一确认的正反例（固定问句与两个固定选项、拒绝即停、取消 / 未回答停止、密钥与大文件阻断、确认后普通内容变化不重问、新阻断重新确认）与运行时恢复正反例（重新交付先核验、doctor 只读诊断、recover 显式指定、陌生 merge / 旧 session 缺证据保守阻断）及冲突恢复正反例（初次冲突固定问答、无回答停止不 abort、撤销、解决并明确继续、仅口头已解决不擅自继续、冲突不转 WIP）。

### `intent-verify-acceptance-contract`

按段落合并 `ph-intent-verify` 的执行语义，调用门禁与整体流程不变：

- **入口契约**：按意图的实际目标用户选择入口，正式入口优先——网页给正式页面、命令行给用户自己终端可复制的命令、后端或库给最小调用方式、桌面或服务给启动与查看方式；业务用户等不适合命令行调用的人不被只给 curl 之类的接口命令，入口不匹配时按「无入口」报告差距。功能没有用户可操作的入口时如实报告并注明原因，该验收点统一记「阻断」；是否属于交付缺陷按意图范围判断——范围或标准要求正式入口而正式入口缺失或故障的属于交付缺陷，记录缺陷与来源，该点用户尚未实际操作不编造「不通过」；范围只覆盖接口、标准并未要求面向该用户的正式入口时只算缺少辅助操作方式，不算实现缺陷。用户明确要求在本次会话补上实现时按用户要求转入普通实现流程办理，本技能不自动调用其他技能。不以自制页面或内部工具代替正式入口。服务只在远端机器 localhost / 127.0.0.1 监听时不当作用户侧可打开地址。"已打开"区分三态：已把入口提供给用户、打开操作返回成功（只说明系统接受了打开请求，不等于用户侧已加载）、页面在用户侧真实加载或用户确认看到，只有第三种可称"已打开"；宿主工具自身的失败与产品自身故障分开记录来源。新增辅助工具须用户另行授权且其准备属于另行任务，向用户交代该任务的范围与恢复条件，不得 mock 或伪造业务结果、只用真实调用，且辅助工具只证明对应能力、不代替正式入口的验收点。
- **验收点契约**：一轮一个点，一个点是一个独立验收结果，可含多个操作步骤；不合并多个独立判断，不扩张标准。标准覆盖多端（网页 / 命令行 / 接口）或多角色（如管理员 / 普通用户）时逐端逐角色验收。预期观察方式按标准定：异步按标准观察「受理」或「完成」，不一律等完成，也不把受理冒充完成；对完成的观察是有界的——在观察预算内等待或轮询，不无限等待也不一概禁止轮询，观察预算按标准或与用户约定，预算到点任务仍在处理中记「未验收」（观察预算到点不等于产品失败阈值，不记「不通过」），注明当前状态并留下可恢复的线索（任务标识、查询入口、恢复方式，含凭据的先脱敏），是否继续等待由用户决定，不自动定时重查；文件类标准实际取得文件并核对内容，不以"已生成"提示代替；导航权限类标准从真实导航路径以对应角色进入验证，深链直达不证明该标准。验收点的验证内容、入口、操作步骤、输入与预期写在用户可见的消息正文里，不只留在工具调用参数或执行日志中。
- **反馈契约**：用户反馈四态（通过 / 不通过 / 阻断 / 未验收）与代理预检证据分离记录；两者矛盾时先澄清反证再记录，澄清时核对确认对象、环境、输入与角色是否与本验收点一致，澄清是核实事实、不借此修改验收标准；不直接记通过，也不替用户编造未发生的不通过。
- **环境与记录契约**：文档写明本身不构成授权——文档引用的脚本与配置先只读核实其真实目标与副作用（对照脚本与配置实现，弄清实际执行什么、会写入什么），再核实执行在本次验收授权内才执行；项目说明缺失时先只读查脚本与配置实现，核实所需动作在授权内后才执行；不默认重启、安装、改配置、公开端口、引入付费服务或写生产；向目标服务发起请求前先核实该服务属于当前项目且在本次授权的验收环境内，不以 localhost / 127.0.0.1 上某端口可连通就默认其归属本项目，也不探测与本次验收无关的服务或端口。已授权操作的缓存、日志等正常副产物不为此重复征求授权，用户已明确授权且条件未变化的操作不重复征求授权；但该例外不豁免对项目真实状态的写入——tracked 文件、快照、数据库真实数据不因操作已授权而免于识别与核查，执行前先识别会写入什么、执行后核查实际变化，发现预期外的修改立即停止、报告实际改动，不自动回滚，等用户决定；文件被 .gitignore 忽略不等于写入安全；能只读完成时优先只读；只读会话不执行会产生写入或外部副作用的准备、也不启动会写缓存或日志的服务。「记录」逐项追加日期、环境、入口、角色、已知构建（按实际可得信息记录，无 commit 等标识时如实说明、不编造、不因此阻断）、验收点、用户反馈、预检证据位置与结论，不含秘密、敏感输入与带凭据的 URL（必要时脱敏）；非只读模式只追加目标意图的「记录」节，只读模式不写任何文件也不准备写操作；中断恢复只重验受影响点，尚未操作或用户跳过的点记「未验收」，宿主工具故障受阻的点在工具恢复就绪后重新提交相关验收点。
