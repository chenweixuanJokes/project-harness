# 1.1.13 → 1.1.14

## why

1.1.13 及更早的 worktree 流程把未提交改动分成两套不一致的处理：进入时源工作区脏一律停止、把清单交用户自行处理；退出提交却按 staged / unstaged 分级默认普通提交，只有分级无法判定（两者并存或含 untracked）时才停下来开放式问"这次提交要包括哪些"。实际执行中出现三类问题——同一处脏工作区在进入与退出被区别对待，用户不知道下一步该做什么；开放式问句没有固定选项，回答无法直接对应一个可执行决定；更严重的是，"用 ph-worktree-exit 收口"容易被当成对 `wip:` 提交本身的授权，分级默认提交可能在用户只看了摘要、没确认范围时就把混合改动收进一个提交。本版统一为"WIP 统一确认"：凡因未提交改动实际阻断的 worktree 操作，都先展示目录、分支、完整清单与拟用提交信息，再实际调用问答工具提出固定问句、只给两个固定选择；问句问的是"是否采用 `wip:` 提交解决当前这次阻断"，不是对文件内容的逐项审批；未确认一律停止。同时，受确认的提交不再由 Agent 手写拼装，而由运行时脚本统一的 `wip` 子命令执行（dry-run 只读，确认后显式 `--apply`）；脚本不能也不需要证明真实用户确认，人类确认永远发生在调用之前。

同时，1.1.13 的合并冲突恢复只有一行"继续用 continue，放弃用 abort-merge"，放弃时问的是开放式问句"你是自己改完后继续合回，还是放弃这次合回"，没有固定选项；何时可以 continue、abort 的授权边界、冲突现场与 WIP 的关系都没有约定，实际执行中出现用户口头说"改好了"就被当作继续授权、冲突条目被想当然收进提交、Agent 自行代改冲突文件等情况。本版把冲突恢复并入统一确认机制：先只读确认真实冲突态（存在 `MERGE_HEAD` 与未合并条目）并列明冲突清单，再实际调用问答工具提出固定冲突问句，只给"保留现场，我解决后继续""撤销这次合并"两个固定选择；继续须用户明确"已解决并暂存，请继续"并只读核验，撤销由该选项本身授权且仅本次。本版同时给运行时补齐恢复与校验能力：`continue` 与 `abort-merge` 执行前依据 session 合并快照核对 merge 身份，旧 session 缺新增证据时保守阻断，用只读 `doctor` 诊断、显式 `recover` 恢复，不猜测、不声称能恢复所有旧 merge。

同时，本批对 PH 技能集做整体收缩与上游集成：`ph-memory-*`、`ph-intent-*`、`ph-docs-sync` 等九个受管技能退役，PH 自身只保留 `ph-init`、`ph-merge-update`、`ph-worktree-enter`、`ph-worktree-exit`；原来由这些技能承载的意图录入、记忆与文档同步流程降级为代理在普通会话按规则文档执行。十个规格驱动技能（`ph-analyze` 等）与 `.specify/` 共享基础设施改为从 GitHub Spec Kit 的固定正式 tag+commit 用官方生成器安装（统一改 `ph-` 前缀并记录来源映射），不再以手工维护的 scaffold 技能承载；`ph-sure` 与 `intent-verify-acceptance-contract` 是本批未发布草稿中的迁移项，随技能集收缩一并撤销，不再发布。宪法（`.specify/memory/constitution.md`）通过上游项目模板覆盖机制（`.specify/templates/overrides/constitution-template.md`，优先级最高）落地 PH 约定：管理区逐篇引用 `docs/约束规范` 实际文档而不复制正文。worktree 提交与冲突恢复改为共享单一脚本 `.agents/scripts/ph_worktree.py`。

## to

PH 1.1.14：必需 Skill 变为四个（`ph-init`、`ph-merge-update`、`ph-worktree-enter`、`ph-worktree-exit`）加十个由上游 GitHub Spec Kit（`github/spec-kit`）固定正式 release 生成的规格驱动技能；项目技能总数十四个。五项迁移：

### `worktree-wip-confirm`

- **统一 WIP 确认**，同一套规则适用于三个位置：`ph-worktree-enter` 的源工作区（创建被脏状态阻断时）、`ph-worktree-exit` 的任务树（交付前有 staged、unstaged 或 untracked 内容时，不再按分级默认普通提交）、`ph-worktree-exit` 的合并目标源工作区（合并被脏状态阻断时，`wip:` 提交做在源工作区）。流程：先只读 dry-run，列明所在目录、当前分支、staged / unstaged / untracked 完整清单与拟用的 `wip: <说明>` 提交信息，用于说明现场与安全筛查结果；随后按 `Git与并行开发.md` 第 2 节的**固定问句模板**（只替换目录、分支、清单、wip 说明、后续动作五个变量）**实际调用问答工具**提问，两个选项文案固定为字面"是""否"，不添加其他预设选项，也不禁用宿主自带的自由输入（自由输入按其本意处理：同意才提交）；没有可用问答工具或工具故障时，按《对用户提问》的降级规则用可见文字提出同一模板并等待回答。不开放式问"怎么办 / 要包括哪些"。WIP 确认问的是是否采用 `wip:` 提交解决当前这次阻断，不是对文件内容的逐项审批。
- **单次 apply 组合调用**：答"是"授权的是本次组合调用——enter 的受确认 WIP 提交与隔离工作区创建、exit 的任务树受确认 WIP 提交与交付，各在单次 `enter --apply` / `exit --apply` 内由运行时脚本一次完成，不拆成"先 wip 再进入 / 退出"两次脚本调用；`--wip-message "wip: <说明>"` 连同绑定 dry-run 快照的 `--expect-*` 参数（enter：`--expect-source-branch`、`--expect-source-head`、`--expect-staged`、`--expect-unstaged`、`--expect-untracked`；exit：`--expect-branch`、`--expect-head` 与同三组路径集合）一起传入，缺任一绑定（含缺失或空的 `--wip-message`）、或分支、HEAD、拟提交路径/状态集合与 dry-run 不一致时脚本整单拒绝并要求重新预检，拒绝发生在任何 `git add` 之前——绝不先暂存再失败，防止把提交落到别的分支或沿用旧确认提交新的改动范围。独立 `wip` 子命令保留给用户直接使用（自有五绑定），技能流程不再使用它作为进入 / 退出的前置步骤；合并目标源工作区的 WIP 是合并目标自己的阻断，按统一确认后单独执行一次源工作区提交，再继续 `exit --apply`。`exit --apply` 在任务树 WIP 提交之前先校验合并目标可交付（目标分支未变、无进行中的 Git 操作、源工作区 clean）：源区处于合并中等不可交付状态时整单先行阻断，任务树没有任何暂存或提交副作用。
- **授权与停止语义**：用户答"是"后才执行；答"否"、取消或未回答时保留全部改动并停止创建 / 暂停交付，不 stash、不丢弃、不改用其他提交方式、不换问法重问。确认后到这次提交实际执行前：分支、HEAD 或拟提交路径/状态集合发生变化（新增、删除或路径状态在 staged / unstaged / untracked 之间转移）时阻断并重新预检、重新确认，不沿用已消费的确认覆盖新变更；同一已展示路径的普通内容修改不需要重新确认（不逐字节比对文件内容）；授权不是长期授权：该提交一经执行授权即消费，该阻断场景结束后再次被未提交改动阻断（包括后续步骤、下一次交付或该工作区再次变脏），按当时的现场重新确认。WIP 确认只覆盖这次 `wip:` 提交，不授权普通提交、清理或任何安全检查豁免；`ph-worktree-exit` 开头的授权句已改写——调用本技能表示用户授权完成必要的验证与合并，任务树与源工作区的 WIP 提交各自按"提交范围"取得确认，调用本技能本身不构成任何提交确认。用户已在本次会话单独明确指定的正式提交（范围与消息齐备）仍按指定执行，不擅自改成 WIP。
- **统一脚本与运行时扩展**：受确认的 `wip:` 提交由运行时脚本统一执行，不由 Agent 手写 `git add` / `git commit` 拼装；提交把 staged、unstaged、untracked 一起收进，ignored 排除，不盲目 `git add -A`；受确认提交完成后脚本只见 clean 工作区。脚本自身不向用户征求授权，脚本无能力证明真实用户确认，其安全分级只在 `--apply` 时兜底拦截其不接受的状态，人类确认由 Skill 流程在调用 `--apply` 前完成。运行时同步扩展：`exit` 不再接收提交信息（兼容接受旧 `--message` 参数但绝不据此提交），任务树提交一律由单次 `exit --apply` 内的受确认 `wip:` 或用户单独指定的正式提交完成；`exit` dry-run 对合并目标源工作区的脏状态改为只读报告 `sourceDirty`（apply 前仍强制 clean），`enter` dry-run 报告 `sourceDirty` / `wipPlanned` / `wipRisks`；新增只读诊断 `doctor`（无 `--apply`，不做修复）、显式恢复 `recover`（`--session <session JSON 路径> --action archive|adopt`，目标与操作由用户显式指定：archive 仅适用于隔离目录已清理或目录不存在且未登记的残留记录，adopt 仅适用于 creating 记录且现存登记 worktree、分支与 initialTaskHead 吻合）与重新交付 `redeliver`（仅适用于 session 处于 `committed` 或 `merge_verify_failed` 且任务分支在其后出现新提交，先核验再交付）；session 合并快照新增 `mergeSourceBranch` / `mergeSourceHead` / `mergeTaskHead`、`sourceWipCommit` / `taskWipCommit` 字段，新增字段非必填、旧 session 只读兼容，迁移不覆盖现有 session。
- **安全筛查保持**：WIP 提交只收进通过安全筛查的路径；疑似密钥文件或内容、异常大文件、ignored 文件与未解决的冲突不得为 WIP 或任何提交收进，也不得绕过安全门禁，须如实列为剩余阻断由用户处置。存在无法纳入的非 ignored 变动时，创建 / 交付在其被用户处置之前保持阻断：脚本对这类状态整单拒绝、不部分提交，即使其中部分路径已另行经授权提交，也不得把该工作区当作干净继续操作或调用 `--apply`。禁止 `git stash`、`--no-verify`、`reset --hard` 的既有约束不变。
- **冲突恢复固定问句**：`ph-worktree-exit` 遇合并冲突保留 Git 标准 merge 状态，先只读确认存在 `MERGE_HEAD` 与未合并条目并列明冲突清单、依据 session 合并快照核对 merge 身份，再按 `Git与并行开发.md` 第 4 节的固定冲突问句模板实际调用问答工具提问（只替换目录、任务分支、源分支、清单四个变量），两个选项固定为"保留现场，我解决后继续""撤销这次合并"，不添加 stash、丢弃、一键选 ours/theirs、Agent 代解决等其他预设选项，也不禁用宿主自带的自由输入。保留现场即停止等待，不立即 continue、不轮询；用户明确说"已解决并暂存，请继续"时只读核验无未合并条目、核对 merge 身份、session 与任务分支未变、merge 状态吻合，才执行 `continue --apply`，既有具体授权不重问；仅文件无冲突标记、或口头说已解决而没有明确要求继续，都不是继续授权。"撤销这次合并"是仅本次 `abort-merge --apply` 的单独授权，执行前说明冲突解决的编辑会被撤销并只读核对 merge 身份，不自动重试 exit、不删除任务分支或隔离目录。取消、跳过或未回答同样停止：不 abort、不做 WIP、不换问法重问。用户明确委托 Agent 解决冲突属单独授权，不能从退出技能、WIP 或保留现场选项推导；冲突条目涉及业务取舍仍停止交用户。新一次 merge 冲突重新提问，不复用旧授权。现场与 session 登记不符（陌生 merge）或旧版本创建的 session 缺少新增证据、无法核对 merge 身份时保守阻断，不猜测补齐：先 `doctor` 只读诊断，确需恢复登记由用户显式指定目标与操作（`recover`），recover 不能恢复所有旧 merge，诊断与恢复之外的状态交用户处置。
- **冲突态优先于 WIP 流程**：合并前源工作区或任务树的脏改动按统一 WIP 确认处理；merge 已发生冲突后，未合并条目不得转成 WIP 或任何提交收进，冲突全部解决并暂存后由 `continue` 生成的合并提交不是 WIP 提交，清理隔离目录仍另行确认。冲突问句只属于 `ph-worktree-exit` 自身流程；另起的 `ph-worktree-enter` 调用遇冲突态不问 WIP、不创建工作区，直接提示用户处于合并状态、等合并完成后再重新调用，不转交冲突恢复流程、不自动弹冲突问句。
- **规则索引与样例同步**：`Git与并行开发.md` 的"WIP 不得静默执行"与退出提交两段改写为统一确认口径，并新增固定问句模板节；异常处理表合并冲突行与新增冲突固定问句段同步冲突恢复口径；`.agents/AGENTS.md` 并行开发规则中"进入 worktree 前遇到未提交改动必须停止"一条改写为统一 WIP 确认口径，并新增合并冲突恢复条目；两个 worktree Skill 的 `evals/evals.json` 合并统一确认的正反例（固定问句与两个固定选项、拒绝即停、取消 / 未回答停止、密钥与大文件阻断、确认后同一已展示路径的普通内容修改不重问、分支 / HEAD / 路径或状态集合变化阻断重新预检重新确认、新阻断重新确认）与运行时恢复正反例（重新交付先核验、doctor 只读诊断、recover 显式指定、陌生 merge / 旧 session 缺证据保守阻断）及冲突恢复正反例（初次冲突固定问答、无回答停止不 abort、撤销、解决并明确继续、仅口头已解决不擅自继续、冲突不转 WIP）。

- **生成规则（默认最小、无编造、无丢失）**：`specs/` 采用上游默认根（仓库根 `specs/`，不存在则创建，不因新项目没有 specs 阻断）；不从 `.specify/feature.json` 的单一 feature 反推根，也不改写已有活动 feature 指针。`docs/意图/待办/`、`实施/`（兼容早期 `进行中/`、`已完成/`）下的每个条目生成 `specs/intent-<intent_id>/spec.md`：只逐字摘录原文内容，目标 / 范围与非目标 / 关键约束 / 验收标准四节按模板节别名映射（最旧 c805d8f 模板的「非目标」归入「范围与非目标」，不误标缺失），缺失节**或空节**标注 `NEEDS CLARIFICATION`，不编造优先级、技术方案、成功指标，不生成 plan / tasks 文件；解析保真——原文重复的同名小节全部逐字保留（不因映射去重丢内容），代码围栏（``` 与 ~~~）内的 `##` / `#` 行不当作小节或标题，其余小节（背景、记录、访谈依据、计划交接等）与引言逐字保留并标注原文为必读出处，交付与验收结论不丢。头部记录来源路径、原 intent_id、源内容 sha256 与迁移时 status_dir；Status 照录历史状态（待办 Draft、实施/进行中 In Progress、已完成 Complete、未识别 Unknown），不把已完成重开为 Draft，也不据实施目录判完成，不自动重新验收、不判通过；frontmatter `status_dir` 与物理目录同属已知状态根（待办 / 实施 / 进行中 / 已完成 / 已废弃）但不一致时在规划期报冲突（如物理已完成、frontmatter 待办不得静默重开），缺 `status_dir` 或未识别值保持兼容照录不冲突。spec 内容是源字节的纯函数（无时间戳），中断重跑可逐字节识别自己的半成品并续装。
- **映射账本**：`specs/.ph-intent-ledger.json` 持久保存在项目内、跨版本有效：每条记录 intent_id、来源路径、源哈希、Spec 路径、生成时 Spec 哈希与 status_dir；已废弃 / 访谈条目进 `history_only`。目标目录按 intent_id 派生，**账本已记录的 Spec 路径永不重算**（历史稳定映射，已持久路径不移动）；不同 intent_id 坍缩到同一目录名（如全部非 ASCII id 坍缩到 `unnamed`）时，后到的条目加确定性消歧后缀（intent_id 的 sha256 前 8 位）避免互相覆盖，真实重复的 intent_id 仍报 duplicate source id。重复源 intent_id、目标 Spec 路径被非迁移产物占用（同名已有 spec，报错附恢复路径：把已编辑的 Spec 移开重跑迁移重建基线与账本，再把修改并回）、大小写归一后同名的 Spec 目录（case-insensitive 文件系统会互相覆盖）、以及 `specs/` 根或 feature 目录被普通文件 / 软链占用（dry-run 明确报冲突，apply 不裸崩）都在规划期阻断整次 apply；`docs/意图/` 管理根下出现符号链接（目录或文件，含根自身）一律 fail-closed 拒绝——普通 rglob 会静默跳过链接子目录使条目消失；新 Spec 文件用独占创建落盘（`os.link` + unlink，绝不覆盖已有名）；迁移后源文件被改动的阻断 apply 与 verify（原文件是只读历史，恢复其字节或把变更写进对应 Spec）；Spec 已被用户修改的不覆盖（`spec_user_modified`，只报告）；历史索引被用户修改的保留并报告——判定不依赖账本：账本丢失（如中断后重跑）时，与当前确定性渲染逐字节一致（或账本记录过）的索引照常重写，其余既有索引一律按用户内容保留，重建账本后重复执行仍幂等保留。账本、历史索引、Spec 与 feature.json 的写入全部带祖先软链 / junction / 硬链 containment 校验，verify 同样校验（含 history_only 原件）。
- **选择已有迁移 Spec**：`ph_merge_update.py select-intent-spec --repo <仓库> --intent <intent_id>`（或 `--spec specs/<dir>` / `specs/<dir>/spec.md`）显式把某个已迁移 Spec 选为当前 feature：默认 dry-run，`--apply` 仅在 `.specify/feature.json` 缺失时写入 `{"feature_directory": "specs/<dir>"}`——指针值是 feature **目录**（上游 common.sh 自行拼 `<dir>/spec.md`，写 spec.md 文件路径会解析成 `spec.md/spec.md`，该解析已用真实上游脚本实测）；文件已存在且指向其他 feature 时拒绝覆盖（改用 `SPECIFY_FEATURE_DIRECTORY` 环境变量或手工调整）。迁移与验证从不改写已有活动 feature 指针。
- **门禁**：verify 与 finalize 校验本项必须 `applied`，并核对 `specs/.ph-intent-ledger.json` 存在、schema 正确、每条记录的 Spec 与原文件都在且逐字节等于账本记录（原文件漂移即阻断并给出恢复指引）、Spec 目录间无大小写归一冲突、`docs/意图/历史索引.md` 在且非空且关键声明仍在（映射以 `specs/.ph-intent-ledger.json` 为准、select 命令与 `SPECIFY_FEATURE_DIRECTORY` 的选择方式；用户备注不破坏校验）、三个产物路径（含 history-only 原件）的祖先 containment 都成立；重复 finalize 幂等（已迁移条目跳过，不改变仓库）。
