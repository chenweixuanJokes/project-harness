# <标题>

`intent_id` 在移动时保持不变；新意图 `type` 为 `feature` / `issue`。`status_dir` 与物理目录一致，默认 `待办/新特性` 或 `待办/问题记录`，启动后改为对应 `实施/` 路径。`clarification_status` 为 `pending` / `clear`，只说明目标是否澄清，不表示已获审批或实现。

`interviews` 引用纪要，`related` 引用其他材料，均使用仓库根相对路径。正文 Markdown 链接按所在文档目录解析。流程见仓库根路径 `docs/约束规范/工程规范/意图与访谈.md`；这里使用路径文字而非模板相对链接，避免复制到不同状态目录后断链。实际纪要的可点击链接必须按目标文件位置生成并核对。

## 背景

谁在什么场景遇到了什么问题，为什么现在需要改变。已知事实注明来源，未知事实不补写。

## 目标

用户希望达成的结果，而不是预设的技术实现。

## 范围与非目标

本次覆盖哪些场景，明确不做什么。

## 关键约束

会影响结果的边界、依赖与既有决定；区分用户决定、已核实事实和假设。

## 验收标准

可观察、可验证的完成判据。目标和验收不清楚时不假装可以开始实现。

## 待澄清问题

列出仍会改变目标、范围或验收的关键缺口。没有缺口时写明无，并给出依据，不靠固定问卷判定充分。

## 访谈依据

列出本意图引用的纪要及一句话定位；实际问答保存在纪要中，不在此复制第二份。

## 计划交接

可写时须先将本意图迁入对应实施目录再按 `docs/约束规范/工程规范/意图与访谈.md` 整理：当前目标、范围、约束、验收、已有决定、代码线索、风险和待研究技术问题。这是进入原生计划模式的输入，不是完整实施计划；进入实施不等于计划获批或业务代码授权。实现完成的用户验收由用户逐点进行，结论记入「记录」节。未准备时如实留空，不宣称已规划。

## 记录

按时间追加重要变化。启动实施或废弃前记录日期、目标目录、原因及证据，再移动文件并更新状态路径、相关链接与沿途 README；交付结果也在此记录，目录保持实施不变。保留编号和历史。废弃不等于删除代码或清理分支。
