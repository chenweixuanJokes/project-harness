# 初始化与文档补全

Last verified: <填写：YYYY-MM-DD>

> 本文是 PH 接入后、把占位文档补成**本仓库真实约定与现行叙述**的操作指引。它约束怎么盘点、怎么取证、写到哪、何时可写；不替代各域正文，也不授权部署、通知、造记忆或造意图。
>
> `ph-init check` 只证明适配层与目录骨架可用。**check 通过不等于文档补全完成。**

## 1. 目的与边界

补全目标：

- 把通用强制门禁留在约束文，把本仓库真实栈、命令、通道、用例入口填进对应占位符。
- 把现行事实写进 Wiki 与 `.agents/AGENTS.md` 的一句话 / 技术栈，并标出来源与生效状态。
- 存量项目**用旧内容接入**：已有正文优先登记引用（结果记 `复用`），不复制第二套，不重写已有证据的正确内容；代码与文档从缺时按第 5 节逐项反推补齐。
- 不为脑图或清单上的每个叶子预建空文档；同类约定写入已有汇总文，有独立维护者与足够事实时再拆专文并补索引。

明确不做：

- 不改 PH 固定 Skill 与上游 spec-kit 技能；不声称存在 Wiki 纠正 / Wiki 问答 / 记忆纠正 / 用户验收 / 收尾核查的专属调用时机（这些环节由代理按对应规则文档在普通会话执行，补全时也不自动触发；规则源分别是本文、`文档治理.md` 与 `意图与访谈.md`）。
- 不因补全文档自动新建意图、访谈纪要或记忆条目。
- 不从坏代码、过期 Wiki、未核实博客或模型推断倒推强制规则；建议不得自动升级为规范。
- 不先安装模板再盖旧正文：存量内容一律经仓外合并候选（见 3.4）接入。
- 不覆盖项目已有定制。冲突或范围扩展时停止受影响项，保留已核验成果。
- 不实际上线、不发送通知、不上传本仓库代码 / 内网材料 / 秘密到公网。

版本与合并升级由发行源维护，不在本仓库业务文档里改 PH 版本号。

### 1.1 存量内容与旧目录

- **保留内容，不保留旧目录结构。** 最终 `docs/` 根只允许 `README.md` 与 `约束规范/`、`意图/`、`项目Wiki/` 三个目录；接入前的 `docs/specs/`、`docs/domains/`、`docs/plans/` 及其它旧目录、顶层正文必须按内容归并，不留旧目录、空壳或软链作为第二套入口。
- 先建立逐文件的**旧路径 → 新落点**映射：规则归约束规范，领域 / 架构 / 操作说明归项目Wiki，已有计划按真实内容归意图或对应事实 / 规范页。附件与辅助脚本随所属正文迁移，不因整理而执行。README 若含独有规则，先提取进正文，再整理索引，不能当普通索引丢弃。
- 同主题内容合并为一个正文：保留旧文的有效细节与历史记录，将已核验的新摘要整合进去，去掉重复内容；不是把两个版本全文拼在一起。PH 摘要与深链指向归并后的正文，旧规范的效力不因移动而消失。
- 已有计划转换为意图时保留原题、来源、原有标识和日期；缺失字段如实标未知，不推定评审、批准或测试通过。按已有记录确定目录，交付留在实施并在「记录」注明原有结果；源状态与代码矛盾则记录双方证据，不以代码猜历史审批。调试实录不冒充访谈，不造纪要。
- 迁移由会话在**本轮授权**范围内执行；内核不自动搬移或删除。写前保存哈希、映射，并把将被覆盖、归并或移走的原文原样写入 `.agents/archived/<YYYY-MM-DD>-pre-init/`（约定见 [archived/README.md](../../../.agents/archived/README.md)）；核对新正文完整、附件一致、活动引用与各级索引修复后，再把活树里的旧文件移出。仓内这份快照就是可恢复原件，不再要求仓外原文备份。adopt 的 plan JSON 仍在目标仓外生成。不先挪走 canonical 或冲突文件骗过安装预检。
- 活动引用必须改到新落点，包括文档、canonical 与已授权范围内的其它入口；历史引用原话可保留为代码字面并在报告登记映射，不把失效链接继续当导航。涉及业务代码的引用超出授权时登记缺口，不擅自改代码。
- 未获迁移授权、存在内容冲突或中断时，报告受影响项为**未完成**，保留现场与续做说明，不把旧目录长期并存算作初始化完成。旧正文与当前代码 / 锁文件 / CI 矛盾按第 4 节定性；规范冲突记 `冲突` 待用户裁决，不悄悄废止规则。

## 2. 完成标准

一次文档补全交付必须同时满足：

1. 只读盘点已覆盖模块、代码、配置、真实依赖（锁文件）、测试、CI 与既有约束 / Wiki / AGENTS，并写明缺口；旧文档目录已按 1.1 处理。
2. 实际在用的栈已按第 3.2 节留下官方资料记录；离线或查不到的标 `待核实`，不编造版本。
3. 存量正文未被模板覆盖：将被改动的原文已先备份到 `.agents/archived/`；合并经仓外候选与 `sources` 哈希快照完成，已有正文以 `复用` 登记引用，冲突未擅自裁决。
4. 矩阵中适用条目都有落点：已填真实值、登记 `复用`、标明 `不适用`，或因冲突停止并留下续做说明。
5. `.agents/init-report.md` 按第 6 节覆盖矩阵全部独立 id，结果如实，未编造项目记录。
6. Wiki 非模板页的五个字段均为真实值：`owner` / `status` / `last_verified` / `verified_against` / `refresh_trigger`。owner 未知写 `unknown`，不猜人名。
7. 写入的命令若只是从脚本 / README / CI **静态抄出、本轮未执行**，必须标明 `未执行，待核实`。
8. 沿途 README 与相对链接仍指向真实存在的文件；共享 README 由主会话汇总，不出现双写分叉。
9. 失败或中断时：已验收段落保留，未完成项可续做，不因部分成功宣称全部完成。

未完成补全前，不得把占位符、空表或过期叙述当成现行答案。

## 3. 会话流程

严格按顺序。未获本轮写入授权前只读。

### 3.1 只读盘点

先读，不改：

| 类别 | 看什么 | 用来决定 |
| --- | --- | --- |
| 约束与入口 | [AGENTS.md](../../../.agents/AGENTS.md)、本目录各文、前后端 / 测试汇总文 | 已有强制门禁与定制，保留不覆盖 |
| 旧文档目录 | `docs/` 下非 PH 命名目录（如 `specs/`、`domains/`、`plans/`）及其正文效力 | 哪些旧内容可 `复用`、哪些与实态冲突 |
| 代码与模块 | 应用入口、包结构、路由 / API、测试目录 | 有无前端 / 后端、真实边界 |
| 依赖锁 | lock / 清单 / 镜像列表，如 `package-lock.json`、`pnpm-lock.yaml`、`yarn.lock`、`go.sum`、`Cargo.lock`、`poetry.lock`、`composer.lock`、Gradle / Maven lock | 实际在用的语言、框架、中间件 |
| CI 与脚本 | `.github/workflows/`、其它 CI、`Makefile`、`package.json` scripts、构建脚本 | 构建、测试、发布入口 |
| 现有文档 | `docs/` 三域、Wiki 五字段、意图目录是否已有正文 | 哪些是定制、哪些仍是模板 |

盘点按七类证据汇总：**模块、代码、配置、真实依赖（锁文件）、测试、CI、旧约束**。每条证据记具体位置（路径、命令、清单条目、行号），能被他人复核。已有正文优先引用登记，不复制第二套。

在隔离副本上核验时，同时记录复制范围与排除项。`git ls-files` 不包含被忽略的锁文件或 `.java-version` 等必要构建输入；副本缺失不代表原项目不存在。先定向核对原路径与 `.gitignore`，在授权范围内审计并补入非凭据输入，保留哈希和来源；不能为补齐输入复制私有环境文件、依赖缓存或共享 Git 元数据。版本选择器与 lock 只证明声明或锁定值，不证明本轮运行过对应环境。

盘点结论先区分第 4 节四类状态。规范不能从“代码现在就这样写”推导出来；代码只能提供事实候选。纯代码仓库没有任何文档时同样逐项反推：七类证据仍是事实候选，无既有来源的规范条目保持 PH 通用门禁或标 `待核实`，不造规则。

### 3.2 按实际栈查公网官方资料

只查**本仓库锁文件或清单里真实出现**的组件。不预填邻项目的 Kong / Eureka / Apollo / 某前端框架。

每条记录必须能复核：

| 字段 | 要求 |
| --- | --- |
| 组件 | 仓库内名称与锁文件版本 |
| 官方标题 | 页面标题原文 |
| URL | 公网官方或标准文档地址 |
| 版本 | 页面声明的文档 / 产品版本 |
| 访问日期 | 当地日历 `YYYY-MM-DD` |
| 采用理由 | 为何写入本仓库文档（例如锁文件已钉住该主版本） |
| 状态 | `已采用` / `待采纳建议` / `待核实` |

禁止：把业务代码、内网地址、令牌、完整连接串贴到搜索或第三方服务。网络失败或资料对不上锁文件时，条目标 `待核实`，写明缺口，不假装已核验。

公开方法论文档可参考，但有边界：

- [Diátaxis compass](https://diataxis.fr/compass/)：帮助区分教程 / 操作 / 解释 / 参考，**不**把 `docs/` 改成这四类目录。
- [arc42 Architecture Decisions](https://docs.arc42.org/section-9/)：决策要写背景与后果，落点仍是 [架构决策](../架构决策/README.md)。
- [OWASP ASVS](https://owasp.org/www-project-application-security-verification-standard/)：安全控制清单的参考，**不**自动选定 ASVS 等级。
- [Software Engineering at Google, ch.11 Testing](https://abseil.io/resources/swe-book/html/ch11.html)：测试分层思路，**不**自动套用 Google 的覆盖率或测试数量阈值。

目标栈的官方版本与 API 以本次联网结果为准，不把上述四篇的目录或阈值抄进强制门禁。

### 3.3 dry-run 与报告整合

用同一发行根跑 `init` dry-run。内核输出的 `plan` / `skip` / `conflict` / `block` 是**待整合材料，不是施工单**。

会话把 dry-run 输出与盘点结论整合后交用户审阅，至少分四类列出：

- **直接落地**：目标缺失、无冲突，可按脚手架或整合后的候选写入。
- **复用引用**：已有正文可用，登记引用与索引，不重写。
- **冲突待裁决**：旧正文之间、旧正文与代码 / 模板矛盾，写双方证据，交用户决定。
- **不适用与保留**：无该端 / 组件、明确保留的定制与历史证据；旧目录结构不属于最终保留范围。

此时不写盘，也不在项目内生成任何候选文件。四类标题和内核字段留给报告与代理笔记。对用户说明和提问遵守 [对用户提问](./对用户提问.md) 的“通过正确通道实际提问”与“把问题写成可回答的决定”：先说还没改文件，再问这次先处理哪些；冲突单项只问“文档该怎么写”，不要把报告字段或脚本名念给用户。

### 3.4 仓外合并候选与安装

用户明确同意本轮写入范围后（对用户问“现在可以按这个范围写入吗”，不要问内部命令名）：

1. 会话在**目标仓外**（临时目录）生成合并候选 plan JSON，并用同一发行根执行：

```text
python3 <release-root>/scripts/ph_init.py init --adopt-plan <plan.json> [--apply] [--mode auto|portable|symlink]
```

2. plan JSON 契约（字段实现以脚本 `--help` 为准）：

```json
{
  "version": 1,
  "repo": "<目标仓绝对路径>",
  "release_version": "<发行包版本>",
  "sources": {
    ".agents/AGENTS.md": "<正文 SHA256，缺失为 null>",
    "AGENTS.md": "<正文 SHA256，缺失为 null>",
    "CLAUDE.md": "<正文 SHA256，缺失为 null>",
    "docs/README.md": "<正文 SHA256，缺失为 null>"
  },
  "files": {
    ".agents/AGENTS.md": "<候选 UTF-8 正文>",
    "docs/README.md": "<候选 UTF-8 正文>"
  }
}
```

   - `sources` 是合并基准快照：必含 `.agents/AGENTS.md`、`AGENTS.md`、`CLAUDE.md` 三个入口，以及 `files` 的全部目标路径；文件缺失写 `null`，不省略键。
   - `files` 只允许 canonical `.agents/AGENTS.md`（必需）与 `docs/**`；候选由已有正文与脚手架整合，已有正文优先原样保留或引用登记。
   - plan 文件在仓外，不进项目、不改发行树、不写秘密 / 令牌 / 完整连接串。
   - 仅当目标尚无 `.agents/ph.json` 时可用 `--adopt-plan`。已装且版本旧于发行根：由 **init 会话**按发行根 merge-update 步骤做完（inspect → 语义合并 → verify → finalize），不重跑 `init --apply`，不要求用户另开技能。
3. 脚本先核对 `sources` 哈希与目标实态一致才落盘，防错仓、错时点与中途变更；哈希一致**不证明候选内容正确**，语义正确由会话 Agent 负责，细节校验主 Agent 可自查。
4. 先 dry-run 再 `--apply`；安装成功立即用**已装内核**跑 `check`。计划外的文件、部署、推送、发通知、建意图 / 记忆，必须再授权。

### 3.5 分阶段与文件归属

安装完成后按文件归属拆 subagent；同一文件只允许一个写入者。建议阶段：

1. **栈盘点**（只读，主会话或一个检索 agent）：产出七类证据表、有无前端 / 后端、CI 入口、现有定制与旧目录清单。
2. **官方资料**（可按组件并行，只读）：回传第 3.2 节记录，不写项目文档。
3. **写入**（按独立文件并行）：
   - Wiki：`项目概述.md`、`功能地图.md`、`开发指南.md`、领域页、架构三页。
   - 各端：`前端规范.md`、`后端规范.md`。
   - 工程与测试：`测试规范.md`、[安全与配置.md](./安全与配置.md)、[构建发布与运维.md](./构建发布与运维.md)、必要时 [Git与并行开发.md](./Git与并行开发.md)。
4. **共享 README / 入口**：由**主会话**统一更新本轮受影响目录及上级 README，包括 [工程规范 README](./README.md)，以及 `.agents/AGENTS.md` 的一句话与技术栈。subagent 只回传所需索引变更，不抢写共享文件。改 canonical 后按原 mode 同步适配层并重新 check。
5. **覆盖报告**：主会话汇总 subagent 回传的结论行，统一维护 `.agents/init-report.md`（第 6 节）。

失败时保留已验收文件，下轮从盘点结论续做，不重写已核验段落。范围扩展或与原有定制冲突：停止**受影响项**，其它无关文件可继续。

## 4. 来源与生效状态

写入任何句子前先定性。四类不得混写在同一条强制句里。

| 状态 | 含义 | 可落点 | 效力 |
| --- | --- | --- | --- |
| 规范 | 本仓库已接受的强制门禁 | `docs/约束规范/` | 必须遵守；与 Wiki / 记忆冲突时以约束为准 |
| 事实 | 对照当前代码、锁文件、CI 或已执行命令核实的现行情况 | Wiki、AGENTS 一句话 / 技术栈、开发指南 | 现行叙述；`refresh_trigger` 点燃后先重验 |
| 外部待采纳建议 | 官方指南或评审意见，仓库尚未决定采用 | 意图、ADR 草稿，或专文中明确标注“建议、未生效” | 非强制；不得当成门禁执行 |
| 待核实 | 来源冲突、资料不可达或待执行验证的部分 | 原落点，必须带 `待核实` 与缺口 | 不得宣称已核验或已通过；已有门禁不因本轮未运行而失效 |

原有定制（已填事实、已接受规则、已有 ADR / 意图正文）默认保留。要用建议替换定制，必须先停下来问用户，不能在补全过程中“顺手规范”。问法见 [对用户提问](./对用户提问.md)：“要用外面的做法换掉现有规定吗？”

## 5. 条目 → 落点矩阵

下表依据《项目级harness.xlsx》工作表 `项目级harness!A1:F65` 的内容树；表内坐标用于追溯需求，执行初始化不依赖原 Excel。合并范围表示**写入同一批文件**，不是为每个叶子建空文件。无前端 / 无后端 / 未使用的中间件在落点文写 `不适用`，保留目录。

逐条执行规则：

- 每个条目都要有**仓内证据**支撑结论：模块、代码、配置、真实依赖（锁文件）、测试、CI、旧约束中的具体位置；无证据不得记 `已核验`。
- 已有正文覆盖某条目时记 `复用`：保留有效内容，按 1.1 归并到 PH 落点后登记引用与索引；不复制第二套，不为换目录重写已有证据的正确内容。
- 旧正文之间或旧正文与当前实态矛盾时记 `冲突`，双方证据都留，交用户裁决。
- 每个条目的处理结果落入第 6 节覆盖报告；报告未覆盖的条目视为未处理。

## 6. 覆盖报告：`.agents/init-report.md`

初始化补全的**实现记录**：记录做了什么、证据在哪、结果如何。它不是业务意图、不是规范正文、不进 `docs/` 三域，也不因它自动生成意图 / 记忆 / ADR。

形式为表格，每个矩阵条目至少一行，列至少五项：

| 列 | 要求 |
| --- | --- |
| `id` | 第 5 节稳定条目 id；同落点多 id 可合并一行，但不得漏 id |
| `落点` | 最终写入或引用的文件（含章节），或 `不适用` 的说明位置 |
| `仓内证据` | 支撑结论的具体位置：路径、命令、锁文件条目、CI 文件、旧规范条目 |
| `结果` | 枚举五选一：`已核验` / `复用` / `不适用` / `待核实` / `冲突` |
| `说明` | 一句话：核实了什么、缺口是什么、为何冲突 |

结果语义：

- `已核验`：本轮对照仓内证据核实过。
- `复用`：已有正文被引用或登记，未重写。
- `不适用`：无该端 / 组件 / 流程，写明依据。
- `待核实`：证据缺失或来源不可达，写明缺口。
- `冲突`：与旧正文 / 代码 / 模板矛盾，留双方证据，待用户裁决。

覆盖范围：**第 5 节每个独立 id 至少一行**（E1–E2、C61–C65、F3–F34、D35–D39、D40–D44、C45–C50、D51–D60）。PH 通用流程条目（采用既有 Skill 或文档流程的，如 C62 / C63、D51–D57、D58–D60、C50）写**采用声明**即可：结果按实际情况记，不为它们编造项目执行记录。

维护：subagent 回传结论行，**主会话**统一写入与更新，避免双写。补全中断时保留已完成行；续做从报告与磁盘实态恢复，不重跑安装。

同一条目仍有实质缺口或冲突时，`结果` 必须标 `待核实` 或 `冲突`，不能只在页脚登记问题却把矩阵标成全部已核验。全量覆盖表示每个条目均有交代，不表示问题全部解决。代码可纠正当前实现的事实摘要，但与既有强制规则冲突时，只记录差异，不以“代码为准”擅自废止规则。

## 7. Wiki 五字段与命令标注

非 README、非模板 Wiki 页必须是真实字段，不允许用模板空值冒充已核验：

| 字段 | 补全规则 |
| --- | --- |
| `owner` | 由 CODEOWNERS、现有责任声明或用户明确指定确认；提交作者只能提供线索，不等于当前负责人。无法确认则 `unknown` |
| `status` | `draft` / `active` / `deprecated` 必须与正文一致 |
| `last_verified` | 本次对照事实的日期；未核验保持空，并在正文标明 |
| `verified_against` | 提交、标签或路径；没有 Git 信息就写核过的路径列表 |
| `refresh_trigger` | 沿用页内默认或按真实变化收窄，不留空口号 |

命令写法：

```text
<命令>    # 已在本轮执行，通过
<命令>    # 未执行，待核实（抄自 package.json / CI）
```

未执行命令可以登记入口，不能当作门禁已绿。

## 8. 禁令（补全会话）

- 不为 F / D / C 每个叶子建空 `.md`。
- 不先安装模板再盖旧正文；存量内容未经仓外合并候选不得覆盖。
- 不把 `待采纳建议` 写进「必须 / 禁止」句式。
- 不把记忆或意图当初始化产物批量生成。
- 不把 PH check、单测偶发通过或模型总结写成 `last_verified` 证据。
- 不把 init-report 写进 `docs/` 三域或意图目录；不在报告里把建议、未执行命令、未核实条目记成 `已核验`。
- 相对链接指向最终交付中真实存在的文件。已有汇总文优先；在已授权范围内，有足够事实时可拆专文并补各级索引。
- 超出本次用户授权范围或与原有定制冲突时，停止受影响项并报告；不为补全文档顺手改业务代码、部署或创建过程记录。
