# 人读伴读写作规范

> 本文件是 PH 人读伴读（human-readable companion）的唯一完整写作规范。ph-human 技能刷新伴读、十个规格技能（ph-specify / ph-clarify / ph-plan / ph-tasks / ph-converge / ph-implement / ph-constitution / ph-checklist / ph-analyze / ph-taskstoissues）附带生成伴读时，都直接读取本文件，不调用 ph-human，也不自动串联任何技能。

## 1. 伴读是什么、不是什么

伴读是与机器产物并排存放的 Markdown 文档，回答一个问题：**这个产物现在说了什么、为什么是这样、哪些部分值得人注意**。它帮助不熟悉规格流程的同事（评审人、维护者、验收人）在两三分钟内抓住要点。

伴读**是快照解释**：正文开头必须注明它解释的是哪个机器产物、什么时点的版本。伴读**不是**：

- 权威规则或验收源——一切争议以机器产物原文为准；
- 操作手册或教程——不指导“如何做”，只解释“是什么、为什么”；
- 机器产物的替代品——伴读缺失不影响机器产物生效，伴读过期不算机器产物缺陷。

## 2. 文件映射与发布

映射与发布由 `python3 .agents/scripts/ph_human.py` 完成，正文写作遵守本节；脚本命令参数以脚本文档为准：

- 功能目录根部的 `spec.md`、`plan.md`、`research.md`、`data-model.md`、`quickstart.md`、`tasks.md`、`verification.md` → 同目录 `<名字>-human.md`（如 `spec-human.md`、`verification-human.md`）。
- `checklists/<名字>.md` → 功能目录根部 `checklists-<名字>-human.md`；`contracts/<名字>.md` → `contracts-<名字>-human.md`。伴读一律在功能目录根部，不进入 `checklists/`、`contracts/`，避免目录扫描把伴读当成产物。
- 项目宪法 `.agents/project-harness/constitution.md` → `.agents/project-harness/constitution-human.md`。
- ph-analyze 的分析报告与 ph-taskstoissues 的已授权结果属于**本次调用的快照**：分别发布为功能目录下 `analysis-human.md`、`issues-human.md`（快照发布命令），只在对应技能真实运行本次产出后生成，不事后编造。
- 任何 `-human.md` 都不是机器源：没有伴读的伴读。两个嵌套产物扁平化后同名（如 `checklists/api.md` 与 `checklists/-api.md`）会被脚本阻断，改名后重试。
- 正文写到仓外临时文件，经 `publish` 发布；脚本在文末附加机器元数据（来源路径、来源 sha256、类型、产出技能、时间、正文哈希），正文不需要、也不得自己写元数据。

## 3. 开头两件必须写的事

正文第一屏必须包含：

1. **来源与日期**：解释哪个机器产物（相对路径）与生成日期（YYYY-MM-DD）。例：`> 本文解释 specs/001-用户认证/spec.md（2026-09-22 快照）。`
2. **快照声明**（语义等价即可）：说明本文是快照解释，机器产物更新后可能过期，以原文为准。

## 4. 写什么（按机器产物类型）

**spec 人读版**：这个需求要解决什么问题、为谁解决；做了哪些关键取舍（做/不做的边界）；最重要的几条验收标准及其含义。不重复需求条目清单，不新增需求。

**plan 人读版**：为什么选这个方案（引用 research.md 的关键依据）；阶段划分的逻辑；最大的技术风险点。研究文档 research.md 的伴读侧重：查了什么、确认了什么、还有哪些未决。

**data-model 人读版**：核心实体与关系一句话讲清；与现有模型相比变了什么。contracts 各契约的伴读侧重：接口给谁用、关键约束、破坏性变化。quickstart 人读版侧重：跑通验证的前提与步骤逻辑。

**tasks 人读版**：任务清单的主线逻辑（先做什么后做什么、为什么）；并行任务与依赖；哪类任务完成才算交付。verification 人读版侧重：哪些验证实际执行过、结果如何、哪些未执行或不适用及原因——照实转述，不升级结论。

**checklist 各清单人读版**：清单在把什么风险关在门外；哪些项最常出问题。清单结果（通过/未通过）只转述。

**constitution 人读版**：项目当前奉行哪些原则、各约束文件何时适用。原则变更讲清取舍（类似 ADR：背景、决定、后果），不罗列全部条目。

**analysis 快照**（ph-analyze）：本次分析发现的最重要问题与覆盖情况，报告已完整交机器流程，伴读只是给人看的同一份结论。

**issues 快照**（ph-taskstoissues）：本次实际创建的 Issue 与对应任务、依赖关系；仅限真实已授权的创建结果。

## 5. 怎么写

- **问题驱动**：每段围绕一个真实问题（“为什么不用现成的 X？”“哪个约束卡住了方案？”），没有问题就不写那段。
- **讲取舍，不讲优劣**：写“选了 A，因为 B，代价是 C”；不写“A 更优秀”这类无依据判断。
- **保留技术边界**：清晰不等于删掉技术内容。接口路径、字段名、版本号、量化指标该写就写；删掉它们只会让读者回到机器产物。
- **标记未知**：机器产物里本身标注的未决项（NEEDS CLARIFICATION、待确认、未执行），伴读照实标记为未知，不替它下结论。
- **保留可追溯标识**：任务 ID、需求编号（FR-x / SC-x）、Issue 编号在伴读里保持原样，读者能对回机器产物。
- 不写套话（“本文将详细介绍”“综上所述”）、不自评（“本文清晰地说明了”）、不描述生成过程（“根据分析，我认为”）。

## 6. 长度与结构

- 两三分钟读完一条主线：小型产物通常 200-500 字；规格、计划这类万字级密集产物按信息量可上探到千字级，不凑长度，也不为压字数删掉编号与技术边界。
- 结构：来源/快照声明 → 一句话定位 → 若干短节（问题或主题各一节）。表格用于实体对照、验证结果这类天生成对的信息。
- 标题写内容（“为什么自建引导模块”），不写分类（“分析”“说明”）。
