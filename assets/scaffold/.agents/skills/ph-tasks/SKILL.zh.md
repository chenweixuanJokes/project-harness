# ph-tasks 中文对照

仅当用户明确点名 ph-tasks 并要求使用时执行；普通描述、名称提及和下一步建议不触发。明确启动后的继续不要求重复点名，不自动调用其他技能。

# 规划实现任务

读取[开发共同约定](../ph-require/references/process.zh.md)。当前需求与设计审查必须就绪；过期审查或未解决阻断不构成批准。小改动由 ph-small-change 内完成等价检查。

## 执行步骤

1. 读取需求、设计、审查及适用测试/构建规范，检查计划依赖的文件、符号、调用者、已有测试和命令。优先复用实现和测试，不先创造抽象。
2. 按可独立验证的成果和真实依赖拆分，使用稳定 T 编号；修订保留原编号和已完成历史。每项说明需求/设计依据、目的、前置条件、负责文件/符号、具体改动、必要单测、验证与完成标准。
3. 已有代码事实要确定，不能写“如果有辅助函数就复用”。真实运行条件分支和外部未决约束另当别论：描述必要行为并标记真实阻断。不只给脆弱行号，还要标识符号或周围结构。
4. 每个适用实现任务内包含单测编写或更新，Bug 修复包含能复现问题的回归测试。测试由项目规则决定，不取决于用户有没有要求。复用已覆盖测试；纯文档/配置任务采用适当真实检查，不编造单测。
5. 补充必要测试设施、数据、文档、可复用冒烟实现及证据任务。后续 ph-verify-plan 负责成果级检查，不应到那时才发现单测全部遗漏。
6. 标注安全并行组、文件归属、接口依赖和外部资源限制，共享文件和索引有唯一协调者。明确调用 ph-worktree-enter 前工作区分配只是建议，不在此创建分支或 worktree。
7. 参考 `runtime/templates/sdd/tasks-template.md` 写 tasks.md，检查覆盖、重复、缺失依赖、编辑冲突和可判断的完成条件。大型计划可委派限定范围的任务扩写和独立审查，交接前必须整体整合。
8. 记录待执行状态，刷新伴读，报告任务组、测试义务与阻断。建议 ph-verify-plan，不直接建议立即实现。

## 完成标准

实施者能按任务执行而不必重新设计功能。必要单测包含在任务内，全部需求有覆盖或明确阻断，未执行任务没有标记完成。
