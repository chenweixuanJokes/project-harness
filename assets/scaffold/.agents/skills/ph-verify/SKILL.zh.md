# ph-verify 中文对照

仅当用户明确点名 ph-verify 并要求使用时执行；普通描述、名称提及和下一步建议不触发。明确启动后的继续不要求重复点名，不自动调用其他技能。

# 验证交付成果

读取[开发共同约定](../ph-require/references/process.zh.md)。本阶段写验证记录与修复任务，不改应用代码，不提交、合并、退出 worktree 或归档需求。

## 1. 确认受检状态

明确功能，读取原始需求/change、设计/审查、tasks、verify-plan、acceptance 与旧证据，运行只读 status/check。确认当前树是集成后的功能还是某执行者任务分支；后者只能报告局部检查，不能宣称整项功能验收。

记录含未提交改动的代码状态、环境、配置及验证范围，重新判断受变化影响的旧证据。读取项目门禁，不能假设计划已经包含所有强制检查。

## 2. 智能体自测与意图核对

通过真实入口执行成果级检查：主流程、集成、重要异常、权限、受影响回归和适用的界面/视觉/输出质量。使用宿主规定的浏览器或视觉工具及委派能力。缺少必需工具记为阻塞，不用读源码代替运行。

单测已在任务内编写执行；检查证据，代码变化或项目门禁要求时重跑。不新增重复单测规划阶段，不免除规定的全量测试。区分失败、未执行和有依据不适用。对不稳定结果遵守稳定性规范，不无限重试直到变绿。

对照每项原始需求和相关设计，检查缺失、部分实现、矛盾和额外行为。沿真实入口核对每个要求的成果；辅助函数的返回值、拟建界面或已评审设计，都不能证明承诺的行为已经存在。设计未经明确范围决定就遗漏或削弱原需求时，应报告设计缺口，不能认可缩水后的实现。已有测试全绿不证明被遗漏的需求已经实现。

verification.md 记录实际操作、结果和证据，无证据不勾通过。智能体检查通过前不请用户体验成果。

## 3. 将失败转成任务

每个实际问题记录稳定发现编号、需求/检查来源、实际/预期行为、证据及最小可验证修复。按发现/来源搜索已有未解决任务，重复失败更新尝试历史，不重复追加任务。

追加修复任务，不重编号、不重写已完成历史、不暗中扩大范围，要求适当回归覆盖。智能体自测失败就停在此处，建议 ph-implement；本技能不修应用代码、不自动调用下一技能。

设计问题返回 ph-design，意图歧义返回 ph-clarify，新功能需要明确范围处理。无关既有失败保持可见并遵守门禁，不能从结果中暗删。

## 4. 用户成果验收

智能体检查通过后，准备 acceptance.md 描述的实际环境、安全代表性数据和可用入口。交给用户前确认就绪。呈现简短业务路径与需要判断的有用成果，不交日志、SQL 断言或技术异常测试。

通过宿主问答能力取得真实结论，记录回答及关联成果编号。用户不可用、取消、未回答则等待，不推定同意。内部改动无合理手动操作时说明证据替代，并记录明确适用性决定，不编造用户通过。

反馈表明未满足原约定时追加/更新修复工作，建议 ph-implement。新增偏好或范围先分清再改需求。修复后先重跑受影响智能体检查与必要回归；除整体体验变化外，只请用户确认受影响成果。

## 5. 收尾

用运行时分别记录两个决定。所有必需智能体检查与意图核对都在记录状态上通过时，把 `verification` 记为 `passed`，不需要等待用户回答；必需检查失败或尚未执行则保持 `draft`。只有真实用户结论才支持 `acceptance=passed`，只有有依据的适用性决定才支持 `not_applicable`。等待用户或准备其验收环境不会抹去有效的智能体结果，也不允许把用户验收记为完成。

刷新支持的伴读，分别报告智能体验证、验收环境就绪情况、用户验收、未解决发现、集成与归档状态。完整成果就绪后才建议 ph-archive；任务分支完成或仍等用户都不算收敛。
