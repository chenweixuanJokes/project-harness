# ph-intent-verify

把意图的验收标准逐点交给用户确认。`ph-intent-impl` 启动推进只表示意图进入实施并制定规划，不表示实现完成；本技能验收的是用户可感知的真实结果，通过与否由用户说了算。本技能只验收和记录：不修代码、不代替用户确认、不推进意图生命周期状态。

## 调用门禁

- 仅当用户当轮明确点名本技能并要求使用时才执行。用户只描述需求（“验收一下”“演示一下做好的功能”）、在上下文里提到、或讨论技能名称本身，都不触发。
- 门禁只管入口：已显式启动的同一流程内，用户回答提问或说“继续”仍按本流程接收反馈与恢复，不要求每轮重复点名，也不触发其他技能。
- 验收是用户行为：每个验收点都实际提交给用户并等待反馈，宿主有可用的问答工具就实际调用；取消、沉默、“先跳过”都让该点保持未通过，不换通道重复施压。
- 代理自己跑测试、构建或浏览器自测只是预检，结果可写进证据，但不能写成“已验收”。

## 定位与核对

1. 向上定位同时存在 `.agents/ph.json` 与 `.agents/AGENTS.md` 的 PH 仓库，缺失则停止，不自动安装 PH。
2. 读取项目约束与 `docs/约束规范/工程规范/意图与访谈.md`，按编号、路径或描述检索目标意图，通常位于 `docs/意图/实施/`。多个候选时用一次提问让用户选择；已废弃或仍在待办的意图不验收，向用户说明当前状态。
3. 核对三样东西：意图的验收标准、真实实现（代码、配置、功能入口）、可用环境。实现与标准不一致时如实指出差距，不替实现辩护，也不擅自修改标准。
4. 复用已有访谈纪要和「记录」节里的既有结论；已经确认过的事实不重问，用户已明确授权且条件未变化的操作不重复征求授权。禁止写入秘密、个人敏感信息和完整连接串。

## 环境准备

- 复用项目已有环境：按项目自己的说明（README、Wiki、开发指南、已填写的构建与启动文档）准备必要的本地服务。文档写明要运行的脚本、命令或引用的配置时，先只读核实其真实目标与副作用（对照脚本与配置实现，弄清实际执行什么、会写入什么、连接到哪里），再核实该执行在本次验收授权内，才执行；文档写明本身不构成授权，执行始终限于本次验收授权内，不擅自重启服务、安装新依赖、修改配置、端口或数据。
- 项目说明缺失时，先只读查脚本与配置实现（启动脚本、构建配置、容器编排、CI 配置等）弄清环境如何就绪、会产生哪些副作用，再核实所需动作在本次验收授权内后才执行；即便查清了，也不默认重启服务、安装依赖、改配置、把端口公开到外部网络、引入付费服务或写入生产，这些动作仍需用户单独授权。
- 向目标服务发起请求前，先核实该服务属于当前项目且在本次授权的验收环境内：不以 localhost / 127.0.0.1 上某端口可连通就默认其归属本项目，也不探测与本次验收无关的服务或端口。
- 环境无法就绪或所需准备超出授权时，不做猜测性安装或重启：报告缺口与受阻原因，受影响的验收点记「阻断」，等用户决定。
- 已授权操作的正常副产物不因此重复征求授权：按已授权步骤启动与使用验收环境产生的缓存、日志等运行副产物属于该操作的正常副产物，不属于修改产品，也不计入本技能的写入范围。该例外不豁免对项目真实状态的写入：tracked 文件、快照、数据库真实数据不因操作已授权而免于识别与核查——执行前先识别这次操作会写入什么（会改动哪些文件与数据），执行后核查实际变化是否与预期一致；发现预期外的修改立即停止，向用户报告实际改动，不自动回滚，等用户决定。文件被 .gitignore 忽略不等于写入安全，同样按识别与核查办理。能以只读方式完成观察或验证时优先只读，不做会产生写入的等价操作。只读会话中本条例外不适用：不执行会产生写入或外部副作用的准备（如启动会写缓存或日志的服务），已就绪服务的只读使用不受影响。
- 生产环境、真实用户数据和共享服务遵守单独授权边界；本技能不写入生产、不展示或回显秘密。

## 展示真实入口

- 按意图的实际目标用户选择入口，正式入口优先：网页功能给正式页面，命令行功能给用户在自己终端可直接复制的命令，后端或库给最小调用方式（含必要入参与前提），桌面或服务给启动与查看方式。不以自制页面、临时包装或内部测试工具代替正式入口。
- 按宿主实际工具能力把要验收的功能交给用户：区分“代理隔离浏览器里的自测”与“用户自己可见的页面”。可访问的地址不等于已打开，区分三态：已把入口或地址提供给用户；打开操作返回成功，只说明系统接受了打开请求，不等于用户侧已加载；页面在用户侧真实加载或用户确认看到。只有第三种状态才可以说“已打开”。
- 宿主有为用户打开的能力且在本次验收授权范围内时，实际打开要验收的具体功能再请用户确认，不只给一个链接；网页功能同时附上地址和步骤，方便用户自己打开。
- 远端与用户侧区分：服务只在远端机器的 localhost / 127.0.0.1 监听时，用户侧通常无法直接访问；不把它当作用户可打开的地址，也不假称已打开，给出用户侧真实可达的地址（如经授权的转发或域名）或按环境受阻处理。
- 不能假称打开：只能提供隔离会话、无法生成用户可见入口或实际打开失败时，如实说明当前状态，并给出用户自行访问的完整地址与步骤；宿主工具自身的失败（如打开失败、问答工具故障）如实记录来源，与产品自身故障分开记录，不据此把产品记「不通过」。
- 功能没有用户可操作的入口时如实报告「无入口」并注明原因，该验收点统一记「阻断」，不默认自制演示页面或编写工具，本技能不自动实现缺失的产品入口。是否属于交付缺陷按意图范围判断：范围或标准要求正式入口而正式入口缺失或故障的，属于交付缺陷，记录缺陷与来源，该点尚无用户实际操作结果时不编造「不通过」；范围只覆盖接口、标准并未要求面向该用户的正式入口时，只算缺少辅助操作方式，不算实现缺陷，如实报告差距。用户明确要求在本次会话补上实现时，按用户要求转入普通实现流程办理，本技能不自动调用其他技能。
- 确需新增辅助工具（测试页面、脚本等）时，先向用户说明并取得另行授权，其准备属于另行任务，向用户交代该任务的范围与恢复条件（覆盖什么、做到什么为止、中断后如何恢复），本技能不自动实现；辅助工具不得 mock 或伪造业务结果，只用真实调用取得结果，且只证明它实际覆盖的能力，不代替正式入口的验收点。
- 非网页功能用合适入口：命令行给可复制的命令，库或接口给最小调用方式，桌面或服务给启动与查看方式；每个入口都必须让用户能在自己的环境里实际操作。目标用户是业务用户等不适合命令行调用的人时，只给 curl 之类的接口命令不算其入口，按「无入口」如实报告实现与标准的差距，由用户决定解锁方式。

## 逐步验收

- 一轮只验收一个点。一个验收点是一个独立的验收结果，可以包含多个操作步骤（标准要求依序操作时按步骤列出），但不把多个独立判断合并成一个点，也不在标准之外追加内容或扩大预期（不扩张标准）。每个验收点写清四件事：验证什么、在哪操作、输入什么、预期看到什么；这四件事出现在用户可见的消息正文里，不只写在工具调用参数或执行日志中。预期结果来自意图的验收标准，可观察、可判定；验收点覆盖全部标准，不遗漏。
- 标准覆盖多端或多角色时逐端逐角色验收：网页、命令行、接口等不同入口，管理员与普通用户等不同角色，分别取得各自结果，不以单端单角色的结果代表全部。
- 预期观察方式按标准定：异步操作按标准观察「受理」或「完成」——标准只要求受理回执时不一律等完成，也不把受理冒充完成。对完成的观察是有界的：在观察预算内等待或轮询，不无限等待，也不一概禁止轮询；观察预算按标准或与用户约定，预算到点任务仍在处理中时记「未验收」——观察预算到点不等于产品失败阈值，不记「不通过」——注明当前状态，留下可恢复的线索（任务标识、查询入口、恢复方式，含凭据的先脱敏），是否继续等待由用户决定，不自动定时重查。标准要求产出文件时实际取得该文件并核对内容，不以“已生成”“导出成功”之类的提示代替文件本身；导航或权限类标准从真实导航路径以对应角色进入验证，直接用深链打开目标页不能证明导航与权限标准。
- 用户反馈与预检证据分离：代理自测、构建、隔离浏览器等预检结果单独记为预检证据，不写成用户反馈。用户反馈与预检证据矛盾（如预检失败而用户说通过）时，先向用户澄清反证再记录，不把矛盾结果直接记为通过，也不替用户编造未发生的不通过；澄清时核对用户确认的对象、环境、输入与角色是否与本验收点一致，澄清是核实事实，不借此修改验收标准。
- 每轮按 [对用户提问](../../../docs/约束规范/工程规范/对用户提问.md) 的“把问题写成可回答的决定”与通道要求，实际调用宿主问答工具提交该验收点并等待回答；宿主确实没有问答工具、故障无法恢复，或该验收点的问题（如开放性追问）用工具格式无法合理表达时，按该规范的降级与开放问题例外，用可见文字提出同等问题并等待回答，说明限制，不声称已通过工具提问，也不借降级改用代理自测冒充验收。不用内部字段名、目录名或技能名当问句主语。
- 用户反馈逐点记录为：通过 / 不通过 / 阻断 / 未验收。不通过记录用户实际看到什么、与预期差在哪；阻断记录受阻原因；用户明确说稍后或跳过的点保持「未验收」，不算通过。
- 整体结论由逐项状态汇总而成，不另设判级：全部验收点都被用户真实确认为「通过」，本次验收才整体通过；存在任何不通过、阻断或未验收的点时整体不通过，结论里逐项列明各状态有哪些点，不整体放行。

## 失败与恢复

- 不通过时记录可复现证据：操作步骤、输入、实际结果（用户原话或注明忠实转述）、相关日志或截图位置、涉及文件路径，让他人能按证据复现。
- 不自动修代码，不调用其他技能补救，不把失败点标记为已解决；修复由用户另行安排后，本技能可在同一意图上恢复继续验收。
- 中断恢复：读意图「记录」节与上轮进度，只重验受影响点——证据被后续改动推翻或环境、入口、构建已变化的已通过点重新验收，未受影响的已确认通过点不重复打扰用户；尚未操作或用户跳过的点记「未验收」，从下一步继续。宿主工具故障（问答、打开等）受阻的点，工具恢复就绪后重新提交相关验收点继续。

## 记录

- 验收过程写入该意图现有「记录」节，逐项追加：日期、环境（本地服务与访问方式）、入口（地址、命令或调用方式）、角色、已知构建（版本、commit 等已知标识）、验收点、用户反馈（原话或忠实转述）、预检证据位置、单项结论与整体结论；不写密码、令牌、私钥、完整连接串等秘密，验收中的敏感输入与带凭据的 URL（如含令牌、密码的地址）同样不落记录，必要时脱敏。已知构建按实际可得信息记录，拿不到 commit 等标识时如实说明，不编造，也不因此阻断验收。
- 写边界：非只读模式下本技能只追加目标意图的「记录」节，不写其他文件；只读模式不写任何文件，也不准备写操作（不生成待写入文件、不暂存改动），逐项材料保留在会话中并说明“待归档、未写入项目”，不能报告已记录。不新建状态、目录或纪要 purpose，不新增 frontmatter 字段，不移动意图文件。
- 「记录」中的验收结论是事实记录，不自动授予提交、合并、发布或部署授权。

## 边界

- 不自动 commit / push，不切分支，不创建 worktree，不发布，不改 `template_version` 等升级字段。
- 文档与代码一致性核验、意图录入、启动推进、废弃分别属于各自技能；本技能不代做，也不自动调用。
- 用户没有验收能力或拒绝逐点确认时，如实报告并停止，不降级为代理自测冒充验收。

## 完成标准

- 已定位唯一意图，验收点全部来自其验收标准，覆盖完整且未扩张标准；多端多角色的标准逐端逐角色取得结果；实现与标准的偏差已如实报告。
- 每个验收点都实际提交给用户并经其逐点反馈（宿主有问答工具就实际调用，确实没有工具或开放问题无法用工具表达时按规范以文字等效提交）；用户反馈与预检证据分开记录，矛盾已先澄清；没有用代理自测、沉默、跳过或推荐项冒充通过，也没有替用户编造不通过；异步观察在约定预算内进行，预算到点未完成的记「未验收」并留下恢复线索，未把观察预算到点当作产品失败。
- 环境复用项目已有说明：文档引用的脚本与配置先只读核实真实目标与副作用、核实授权后才执行，文档缺失时先只读查脚本与配置实现，均在授权内准备，未擅自重启、安装或改配置；执行前识别写入、执行后核查变化，预期外的修改已停止并报告而未自动回滚；给用户的入口真实可访问且以正式入口优先，未假称打开，每次宣称“已打开”都有用户侧真实加载或用户确认看到的证据，远端 localhost 未被当作用户侧地址，业务用户未被只给接口命令。
- 无入口的功能如实报告并注明原因，该点记「阻断」；交付缺陷按意图范围判断，范围要求正式入口而缺失或故障的已记录缺陷与来源，仅接口范围的差距按缺少辅助操作方式报告；用户明确要求本会话实现的已转入普通实现流程，未自动调用其他技能；新增辅助工具（如有）均经用户另行授权且属另行任务、已交代范围与恢复条件，未 mock 或伪造业务结果，只用真实调用，且只用于证明对应能力，未代替正式入口的验收点。
- 「记录」节有日期、环境、入口、角色、已知构建、逐项反馈、预检证据与结论，未记录秘密、敏感输入与带凭据的 URL，已知构建按实得信息记录、未编造；整体结论与逐项状态一致，通过必须全部点真实确认；除追加目标意图「记录」外未写其他文件（只读模式未写任何文件、也未准备写操作，未启动会产生写入的准备）。
- 未修改代码、未提交发布、未自动调用其他技能、未越秘密与生产授权边界。
