# 审查设计

读取[开发共同约定](../ph-require/references/process.zh.md)。这是任务规划前的审查，不要求 tasks.md。可以写 review.md 及审查状态，不修改需求、设计或应用代码。

## 执行步骤

1. 完整读取需求、设计及当前来源状态，读取适用约束，并获取足以核实关键判断的代码证据。旧审查文件存在不代表结论仍有效。
2. 将每项需求和用户成果映射到设计位置，检查遗漏、冲突、无依据扩展、交互歧义、失败状态、数据权限边界、兼容和可测试性。原始已确认意图是验收依据，设计不能暗中缩小它。
3. 评估实现可行性、依赖顺序与并行边界，报告没有代码或权威资料支持的假设。不要求先有详细任务清单才能审查设计。
4. 范围适合且宿主支持时，委派独立只读审查，限定文件和具体问题。综合证据而不是统计审查人数。没有子代理则本地完成相同检查并说明限制，不假称发生独立审查。
5. 写 review.md，记录受审来源身份、覆盖情况、稳定发现编号、严重性、证据、关联需求/设计及修正建议。问题必须指出实际后果，不把个人风格偏好当缺陷。区分阻断和可选改进。
6. 有阻断时保持设计未批准，按问题建议 ph-design 或 ph-clarify。不在审查中直接修设计，不降低需求以求通过。无阻断时通过运行时以报告为证据记录设计 reviewed；宿主或用户要求的审批单独保留。代理审查不等于用户批准。
7. 报告结果与下一步，仅设计审查及适用审批通过后建议 ph-tasks，不调用。

## 完成标准

用户能看到设计是否覆盖约定需求、判断依据及任务规划阻断项。无问题结论必须来自实际检查，不能复制一个空问题列表充数。
