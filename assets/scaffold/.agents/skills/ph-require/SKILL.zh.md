# ph-require 中文对照

仅当用户明确点名 ph-require 并要求使用时执行；普通描述、名称提及和下一步建议不触发。明确启动后的继续不要求重复点名，不自动调用其他技能。

# 录入需求

读取[开发共同约定](references/process.zh.md)。本阶段记录意图，不设计方案、不实现代码。

## 执行步骤

1. 判断新建还是修改已有需求。查阅相关项目事实和已有功能，避免重复开发。调查深度与任务相称，不把明确的小需求变成完整 PRD 访谈。
2. 提取问题、目标用户、有价值的成果、范围、非目标、不可违背的限制和用户验收目标。区分用户提供事实、已核实事实、假设和未决事项。
3. 只询问影响范围或验收的缺失决定。问题具体且有依据，不让用户提前选择设计阶段的技术细节。不为完成模板而用合理猜测填补业务未知。
4. 选择明确的功能编号，不改 Git 分支。新建完整需求时查看 `python3 .agents/scripts/ph_sdd.py create --help`，预检 `create --repo <root> --feature <id> --flow full --title <title>`，在本次写入授权内 apply。以 PH home 下 `runtime/templates/sdd/requirement-template.md` 为结构参考，不填无意义内容。
5. 在功能目录撰写 `requirement.md`，分配稳定 FR/NFR 与用户成果验收编号。主成果说明角色、初始条件、代表性操作和可观察的有价值结果。这里是承诺，不是技术测试步骤。未知明确记录；修改决定时保留原文或澄清历史，不暗中替换。
6. 实际完成清晰度检查前保持 draft。历史 `spec.md` 仍可作为映射来源；需要时使用运行时显式接入旧产物的操作，保留原文字节，不伪造已核验状态。
7. 按共同约定发布支持的伴读，报告目标、范围、验收成果和阻塞，建议 `ph-clarify`，不调用。

## 完成标准

读者能说明需求是什么，以及用户如何判断成果满意。未决事项清楚可见。没有编造设计、代码、Git 操作或用户验收结论。
