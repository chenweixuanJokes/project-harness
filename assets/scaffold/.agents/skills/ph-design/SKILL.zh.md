# ph-design 中文对照

仅当用户明确点名 ph-design 并要求使用时执行；普通描述、名称提及和下一步建议不触发。明确启动后的继续不要求重复点名，不自动调用其他技能。

# 设计方案

读取[开发共同约定](../ph-require/references/process.zh.md)。需求须足够清晰；可调查缺失事实，不得暗中决定未决业务问题。

## 执行步骤

1. 读取需求、适用约束、当前架构、受影响源码、接口和测试。有语义工具时用其追踪调用及副作用。只在必要时核实版本和权威外部资料，不把私有项目内容发给外部搜索。
2. 描述产品体验：入口、角色、主流程、可见成果、加载/空/错误/权限状态及适用的无障碍要求。命令行、服务、内部改动描述真实使用者契约，不凭空创造页面。
3. 描述实现边界：复用组件、改动模块、数据流、接口与数据契约、错误处理、兼容、迁移、安全和运维影响。文件与符号位置以核实结果为准。现在查清代码事实，不把“如果 X 存在就复用”留给实施者。
4. 只对重要选择比较备选，说明选项、证据、代价和未决依赖。不为明显局部选择强求备选，不把未知外部行为当成已确认。
5. 参考 `runtime/templates/sdd/design-template.md` 写 design.md，将需求和验收目标映射到设计段落。明确可测试边界和资源需求，不展开完整任务级测试脚本。登记预期项目文档和可复用用例库变化。
6. 标出并行边界和共享接口。共享数据结构、生成文件、依赖锁文件、数据库迁移、公共索引须有负责人或串行处理。worktree 可选，本阶段不创建。
7. 对照原始需求复核。无法满足时暴露冲突，不降低验收目标。ph-design-review 实际审查当前来源前保持设计 draft。修改已审设计后，相关任务和检查需复核。
8. 刷新支持的伴读，展示用户可见行为、重要实现决定、风险和未决项。建议 ph-design-review，不实施代码。

## 完成标准

设计同时说明使用者体验与项目如何实现。每项需求有设计落点或明确缺口。不修改代码、分支、外部配置和验收门槛。
