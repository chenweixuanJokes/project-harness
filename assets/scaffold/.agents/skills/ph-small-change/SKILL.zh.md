# ph-small-change 中文对照

仅当用户明确点名 ph-small-change 并要求使用时执行；普通描述、名称提及和下一步建议不触发。明确启动后的继续不要求重复点名，不自动调用其他技能。

# 准备小改动

读取[开发共同约定](../ph-require/references/process.zh.md)。这是规划入口，不是直接改代码的捷径。减少文档不降低测试和授权要求。

## 适用条件

预期结果和受影响行为明确、范围局部、兼容清楚、可以用有限检查验证时采用。按后果与不确定性判断，不按修改行数。

先调查所谓简单 Bug，再判断是否适用。公共接口、数据迁移、鉴权安全语义、核心业务变化、跨模块广泛影响或未决产品选择应进入完整流程。保留已查清内容，建议对应需求/设计阶段，不自动启动整条流程、不丢弃记录。

## 执行步骤

1. 读取当前行为、相关代码/测试及约束。Bug 明确复现输入、实际和预期行为，区分确认原因与假设。授权内可执行安全调查检查，但准备阶段不实现修复。
2. 事实缺口自行查清，只询问重要用户决定。change.md 写目标、保留行为、非目标、影响位置、已确认原因或未知、最小方案及用户成果验收。
3. 新建适用小改动时先预检再 apply：`ph_sdd.py create --repo <root> --feature <id> --flow small --title <title>`。参考随包 change 模板，不造空需求/设计文件。已有小改动或旧记录保留身份和来源历史。
4. 本次调用内检查简版需求/方案的遗漏和约束冲突。标记 change reviewed 前，逐项列出剩余不确定，判断答案是否会改变拟议行为、兼容或范围。可能改变时保持 change draft，将该决定写成受影响实施任务的阻塞前置，并停止建议实施；问题位于仓外或留给用户验收，都不代表依赖已解决。已经约定的成果只是暂缺演示证明则不同，应明确记录验证限制。记录真实审查，不走形式。
5. tasks.md 使用稳定编号、具体负责文件、前置、必要单测、验证和完成条件。未解决的实施条件须写入受影响任务的前置要求，不能以总体审查标记代替解决。Bug 任务在适用时包含能复现问题的回归测试。复用已覆盖测试，不做无关清理。
6. verify-plan.md 和 acceptance.md 与完整流程语义相同：智能体检查可用成果和受影响回归，用户确认准备好的代表性成果。技术标准即使在旧需求中编号为 AC，也应映射到智能体检查，不能让用户确认测试通过或内部行为未变。直接读取模板和测试规则，不调用 ph-tasks 或 ph-verify-plan。单测仍在 Task 内，现行全量测试要求不降低。
7. 核对覆盖与来源新鲜度，发布支持的伴读。报告适用简易流程的理由、最小方案、检查与阻断。准备就绪后才建议 ph-implement。

## 完成标准

小改动有真实精简的需求/方案、可执行任务、智能体检查及成果导向用户指引。准备请求没有被扩展成实现、建分支、提交或验收通过。
