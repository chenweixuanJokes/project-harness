# ph-docs-sync

把 README、docs 说明性内容与 Wiki 现行叙述和仓库实态对齐：先取证，再核验；默认只读，明确授权后才修，且只修可直接证实的不一致。本技能不做业务开发，不改规则去迁就代码。

**调用门禁**：仅当用户当轮明确点名本技能（如「用 ph-docs-sync 检查文档」）并要求使用时才执行。用户只说“同步文档”“检查文档过期没有”、上下文提及、或讨论技能名称本身，都不触发；升级完成后也不因升级自动运行。

## 何时用 / 何时不用

使用：

- 用户点名本技能并要求检查 / 同步文档：核对 README、docs 配置说明、使用示例、Wiki 是否与当前代码、配置、锁文件、CI 一致。
- 升级或重构后用户点名本技能，要求核对受影响文档（按各页 `refresh_trigger`）。

不用：

- 首次接入或初始化时的文档补全 → `ph-init` 初始化流程（见 [初始化与文档补全](../../../docs/约束规范/工程规范/初始化与文档补全.md)）。
- 适配层检查 / 同步（根 `AGENTS.md`、`CLAUDE.md`、`.claude/skills/`）→ `ph-init` `check` / `sync`。
- 升级 PH、合并迁移 → `ph-init` 会话按 `ph-merge-update` 步骤；本技能不因升级自动运行。
- 实现完成的逐步用户验收 → `ph-intent-verify`（由用户点名）；本技能核对文档叙述，不验收功能。
- 修改约束规范规则、AGENTS 约束正文 → 文档治理 §7 纠正：需用户确认规则变更，不从代码倒推。
- 记忆、意图录入 / 实施 / 验收 / 废弃、worktree。

## 事实源与线索

- **当前代码、配置、锁文件、CI、现行约束是全量事实源。** 当前工作区（含未提交改动）是事实；不要只看已提交内容。
- 近 7 天提交只提供“可能过期”的变化线索：提交标题不能证明实现已落地，找不到提交也不能证明某行为不存在（可能未提交、更早或以别的方式实现）。用户指定提交区间时以指定区间为准，覆盖近 7 天默认。线索只用来优先点名要核对的文档，不限定核对范围，也不据其下结论。
- **搜索覆盖不足不能作否定证据**：在代码、配置或文档里搜索不到某名称或行为，不能证明它不存在（可能命名不同、间接引用、构建生成或在未搜索的位置）；下否定结论须有正面依据（如完整入口清单、依赖闭包），否则报告未知。
- 先读各 Wiki 页 `refresh_trigger`、`last_verified`、`verified_against`；触发已发生且核验日早于该变化，或正文与实态冲突的页，不得再当现行叙述。

## 核验对象

- 仓库 README 与 docs 内的配置说明、使用示例、操作步骤。
- Wiki 非模板页的现行叙述（按 [文档治理](../../../docs/约束规范/工程规范/文档治理.md) §4）。
- 沿途 README 索引的指向与一句话定位。

## 修复边界

1. **只修可直接证实的不一致**：每处修改都有仓库内证据（路径、配置键、锁文件条目、CI 步骤、代码位置）支撑；证据不足的标 `待核实`，不改。
2. **保持原文档结构与术语风格**：不重排章节、不换叫法、不顺手润色；修复最小到能消除不一致。
3. **逐项报告**：每处修改报告文件（含章节）与依据；**没有修改时报告实际核对范围与证据**（核对了哪些文件、以哪些实态为证、缺口在哪），不笼统说“已同步”。
4. **检查请求只读**。用户明确要求同步修复才写文件；写入范围以该次授权为准，范围内无需逐项再问，范围外先问。
5. 文档中的代码片段与实态不符时可修正，但**不伪称运行成功**；未实际执行过的命令与示例不得标“已验证通过”，报告中写明其静态依据（依据哪个脚本、配置或 CI 步骤推导）。
6. **核对示例的完整前置条件，不能只替换命令名**：构建产物来源（脚本指向 `dist/`、`build/` 等生成目录时，示例必须包含或引用前置构建步骤）、工作目录、环境变量与步骤依赖（先安装、先构建、再启动）一并核对；漏了前置条件的示例仍是不一致，要一并修。
7. **配置项分别核验名称、可配置性、默认值**：文档声称的每个配置项，分别确认代码确实按该名称读取、确实可配置、默认值是什么；常量硬编码或输出恰好相同**不构成**“支持配置”的证据。框架默认行为（日志实现、默认端口等）须以仓内锁定的依赖版本与可验证的实现证据为准，不凭框架印象推断；证据不足时报告未知并标 `待核实`，不写成事实。

## 保护与不改写

- 规范冲突不降级规范：代码 / 配置与 `docs/约束规范/` 或 `.agents/AGENTS.md` 矛盾时，只记录冲突并交用户裁决，不改规则迁就代码，也不把代码现状写成规范。
- 历史意图、访谈纪要、Changelog、迁移说明、`.agents/archived/` 与 `memory/archive/` 原件不改写。
- 可执行示例、真实配置文件和业务代码只作为证据，默认不改；确需修改时走正常开发授权，不在本技能内顺手改。
- 保护用户改动：他人未提交的文档编辑不覆盖；与实态不一致但疑似有意的定制，先问再动。
- 不改镜像生成物（适配层副本）、依赖锁文件、内嵌安装的发行材料（`.agents/skills/ph-init/` 内的 scaffold 与脚本）。
- 禁止 `rm`；需要移除的文件先征得用户同意并移入 `~/.Trash/`。

## Wiki 五字段

- 五字段（`owner` / `status` / `last_verified` / `verified_against` / `refresh_trigger`）**仅如实维护**：核验过才更新 `last_verified` / `verified_against`；`owner` 未知写 `unknown`，不猜。
- **局部核对不能谎称整页核实**：只核对了部分段落时，`verified_against` 如实写核对范围，不得把整页标成已核验。
- 普通 README 不强添这五个字段；它们只属于 Wiki 非模板页。

## 不自动做的事

- 不自动把报告 / 核验记录落盘成新文档，不造记忆、不造意图。
- 不 `git commit` / `push`、不部署、不发通知。
- 不改升级相关字段（`template_version`、`.agents/updates/` 等）。
- `ph-init` check/sync 只查适配层，不替代本技能；本技能也不替代初始化补全——接入时的一次性补全仍走 `ph-init` 流程。

## 工作流

1. **确认动作与授权**：区分“只读检查”与“同步修复”。用户指定了写入范围（哪些目录或文件）按其执行；未指定时按核验对象默认范围执行（仓库 README 与 docs 配置说明、使用示例、Wiki 现行叙述），无需再问；仅当授权含糊、范围越界或与项目定制冲突时先问，问句用日常用语，不用内部术语。
2. **取证**：读当前代码、配置、锁文件、CI 与现行约束；`git log` 取近 7 天提交（用户指定提交区间时以指定区间为准）作线索；`git status` 确认工作区实态。
3. **逐项核验**：按核验对象对照事实源；命令示例核对完整前置条件（构建产物来源、工作目录、步骤依赖），配置说明分别核对名称、可配置性与默认值；每项记录一致 / 不一致 / 待核实与依据位置。
4. **修复（仅授权范围内）**：按修复边界逐项修改；每处可复核。
5. **diff 与链接复核**：逐处重读本次修改的 diff，确认只消除了目标不一致、结构与术语风格未被打乱、未夹带计划外改动；核对受影响文档的相对链接、沿途 README 索引与章节引用仍指向真实存在的目标。
6. **报告**：列出修改项（文件、改动、依据）与未修改项（实际核对范围、证据、待核实与冲突缺口）。问答式检查不写任何文件。

## 完成标准

- 每处修改都有可直接证实的依据并已报告文件与证据；无修改时已报告实际核对范围与证据，未谎称已同步。
- 命令示例的前置条件（构建产物来源、工作目录、步骤依赖）已核对，未只替换命令名；配置项的名称、可配置性、默认值分别核验，未把常量或输出等价当配置证据，未凭框架印象推断框架默认行为；证据不足处标待核实，未写成事实。
- 修改后已重读 diff 并复核链接：未引入计划外改动，受影响文档的链接与索引仍有效。
- 未改规范迁就代码；历史意图、纪要、Changelog、迁移与归档原件未改写；业务代码、真实配置、可执行示例未被修改；未伪称未执行的命令通过。
- Wiki 五字段如实维护，未把局部核对说成整页核实；普通 README 未被强添元数据。
- 只读请求未写任何文件；未自动落盘报告、造记忆 / 意图、git 操作、部署或改动升级字段。
