# 意图与访谈

> 意图说明用户希望改变什么；纪要保留如何澄清和决定的证据；实施计划由宿主计划模式制定。三者不能相互冒充，也不自动授予实现权限。

> **1.1.14 起，本目录机制转为只读历史**：存量业务意图已由 `intent-to-spec` 迁移为 `specs/` 下对应的 Spec，后续只在 Spec 中继续维护（映射见 `specs/.ph-intent-ledger.json`，规则与选择方式见 `docs/意图/历史索引.md`）；已废弃条目仅登记历史不重开，访谈纪要原位保留只读历史。本文保留为历史流程与纪要规范的参照，不再用于新增意图条目。

## 1. 职责与入口

意图域没有专属调用技能，录入、推进、验收与废弃由代理在普通会话按本文执行：

| 环节 | 产物与边界 |
| --- | --- |
| 录入 / 补充 | 录入或补充意图及访谈纪要；新建入待办，补充已有保持原目录，不自动制定计划或实现 |
| 启动推进 | 可写时先将唯一目标迁入实施，再准备交接并进入原生计划模式；实施不等于获批或业务代码授权 |
| 验收 | 实现完成后由用户逐点验收唯一意图，结论写入该意图「记录」节；不改代码，验收通过与否由用户确认 |
| 废弃 | 明确原因后从待办或实施移入已废弃，不回滚代码或清理分支 |

这些环节在用户明确要求的范围内执行；普通描述、上下文提及都不自动触发，环节之间也不自动串联。使用本仓库的 旧版 `docs/意图/_模板.md`（已随意图目录退役） 和 旧版访谈纪要模板（已随意图目录退役），不依赖用户主目录中的 Skill、个人记忆库或厂商专属绝对路径。一般“记住这个结论”属于项目记忆；录入需求、规划意图、用户验收和废弃决定属于意图域，不能自动双写。

## 2. 问前调研

先读当前对话、目标意图、历史纪要、相关代码、配置和文档。对每个缺口区分：

- **已核实事实**：记录来源及适用范围，例如实际路由、配置或测试覆盖。能从资料查清的，不向用户重复确认。
- **用户已明确的决定**：保留来源并复用；有新证据冲突时，说明变化后只问受影响的决定。
- **假设**：明确标出，不当作用户要求或代码事实。
- **用户决策缺口**：答案会改变目标、范围、验收或关键取舍，且现有证据不能替用户决定，才值得提问。

调研未完成不等于只能问用户；资料取不到时说明证据限制，不把未知包装成已经确认。不要为了问完固定问卷而询问技术栈、目录、现有 API 等可查事实。

调研范围围绕当前决策：先读目标和直接关联证据，仅在出现真实缺口时扩大。已取得明确答案就停止该方向的搜索；不为录入或废弃一个意图遍历无关模块和全部测试规范。

## 3. 一问一答

每轮只处理一个独立决策，等待用户实际回答后，再决定下一轮。按 “通过正确通道实际提问”（见工程规范/对用户提问.md） 实际调用可用问答工具；文字选项和口头承诺不能替代调用。工具降级、用户取消与专用流程例外按该规范处理。

每问包含：

1. **已查到什么**：简短说明与本问直接相关的证据。
2. **为什么问**：尚未确定的点，以及答案对范围、结果或实施的影响。
3. **一个问题**：不将多个独立问题塞进一句话或多选清单。
4. **选项及推荐**：推荐项置首，标注“推荐”并说明理由，提供合理的替代选择和自由回答入口。遵守宿主问答工具的选项格式。

对用户开口时遵守 工程规范/对用户提问.md 的提问规则，提问前读其“何时需要用户决定”与“把问题写成可回答的决定”。目录名、状态字段、Skill 名只写在纪要或代理笔记里，不要当问句主语，也不要问内部状态名。

推荐必须有依据。尤其在废弃访谈中，不能推荐“价值不足”“预算不足”等未经用户确认的动机，也不把“补充原因后再废弃”这种处理方式冒充原因选项。证据不足时按 “把问题写成可回答的决定”（见工程规范/对用户提问.md） 提出开放问题，取得用户说明的真实原因后再记录；未获原因时保留未决状态。

回答模糊或与现有决定冲突时，只追问影响目标的部分。不能把默认选项、模型推断、用户沉默或用户说“继续”当成对所有假设的确认。

### 示例

已查到导出接口支持单条和批量，但意图没有说明本次需要哪种操作。为什么问：这会改变页面交互和批量失败的验收范围。

问题：本次导出需要覆盖哪种使用方式？

- 单条导出（推荐）：当前意图只描述单条处理，先满足已出现的场景。
- 同时支持批量：纳入批量入口、限制及部分失败处理。

自由回答使用宿主问答工具自带的输入入口，不另加重复的“其他”选项。

这只是问法示例，不能把示例中的推荐套用到不相关的项目。

## 4. 完成与中断

### 4.1 录入

目标对象和场景、当前问题、预期结果、范围与非目标、关键约束、可验证验收标准已清楚，且没有会改变这些结论的关键未决问题，才将 `clarification_status` 设为 `clear`。

没有真实缺口时允许零新增问题：引用已有答案或资料，写明“本次无新增问题”及原因，不虚构轮次。访谈机制的目的是澄清，不是凑问题数。

结束时简短回述目标和关键决定；只在仍有实质分歧时继续问，不固定追加“是否明白”“还有补充吗”。`clear` 只说明澄清程度，不意味着计划获批、已实现或已完成。

### 4.2 计划与废弃

计划准备只补齐影响规划的用户决策，技术方案研究可交给计划模式继续进行；不要重问已充分访谈的目标。可写时须先完成向实施目录的迁移，再继续调研或切换；只读不写，按实际目录报告。

废弃只核实对象、用户真实原因、必要的影响和替代意图，不重做需求访谈。用户已经说明原因且明确要求废弃时直接使用，不再机械问“为什么”。“先不做”可能是延期，不能擅自推定永久废弃。待办与实施中的条目均可废弃；延期则保持原目录。

### 4.3 中断

每轮有效回答后及时保存本轮纪要及相关引用，再提出下一问。无关键结论时不标记完成。可写模式下明确中断或离开任务时将纪要标为 `paused`，记录已知结论和待继续问题；意图有目标缺口时保持 `pending`，不为形式推翻未受影响的历史结论。突然断线可能来不及更新状态，恢复时检查实际内容，不凭旧 `ongoing`/`complete` 字段断言访谈充分。

## 5. 文件与引用契约

### 5.1 意图

新 feature/issue 意图使用 旧版 `docs/意图/_模板.md`（已随意图目录退役）。每条意图为一个 Markdown 文件，`intent_id` 永久稳定；生命周期仍由状态目录决定，`status_dir` 必须一致，不另增状态字段。

- `new`：新建入 `待办/新特性` 或 `待办/问题记录`；补充已有意图保持其当前目录，不因补访而改派。
- `impl`：唯一可写目标先迁入对应 `实施/`，再调研与交接计划模式。已在实施则幂等继续；实施包含准备、规划、开发与验收，不等于计划获批或业务代码授权。迁移顺序、只读与失败处理见下文“模式交接与权限”。
- `verify`：实现完成后由用户逐点验收，单项与整体结论（通过 / 不通过 / 阻断 / 未验收）记入意图「记录」；验收不新增 frontmatter 字段、状态目录或纪要 purpose，也不修改业务代码。启动推进只表示进入实施与规划，不代表实现完成。
- `drop`：从待办或实施移入已废弃；原因、授权与安全移动规则不变。
- 完成：不设已完成目录。交付后在意图「记录」注明日期与验收证据，意图留在实施；不因进入实施、计划获批或实现进度自动记录交付。
- 旧目录 `进行中/` 已取消：存量条目按证据迁入待办（仅录入澄清）或实施（已启动推进），目录与索引随之移除，迁移依据追加在意图「记录」；不再保留进行中状态。

- `interviews`：纪要文件的**仓库根相对路径**列表。
- `related`：其他相关材料的仓库根相对路径列表，不用它代替新纪要的 `interviews`。
- `clarification_status`：`pending` / `clear`，与生命周期和审批分开。
- 正文中的 Markdown 链接仍按**当前文档所在目录**解析，不能直接把仓库根相对路径伪装成可点击相对链接。

编号使用 `INT-YYYYMMDD-短主题`，文件名为 `<intent_id>.md`。在整个意图域查编号和目标路径冲突；碰撞时使用可读后缀，不覆盖、不靠覆盖解决同名。

### 5.2 纪要

新纪要使用独立 `interview_id`，不是新的业务意图。文件固定放在 `docs/意图/访谈纪要/<interview_id>.md`，编号为 `IV-YYYYMMDD-HHmmss-短主题`，同样检查冲突。

| 字段 | 语义 |
| --- | --- |
| `interview_id` | 本次会话纪要的稳定编号 |
| `intent_id` | 关联的一条意图编号，不随意图移动改变 |
| `purpose` | `capture` / `plan` / `abandon` |
| `status` | `ongoing` / `complete` / `paused`，只描述本次访谈 |
| `created` / `updated` | 当地日历日期，`YYYY-MM-DD` |
| `related` | 其他证据或前次纪要的仓库根相对路径列表 |

一次访谈会话一个文件，内部按轮次追加。后续新会话或目的改变时另建纪要并关联前次；同一轮工具重试先查记录，不重复追加。历史纠正追加新记录，不删除或重写旧答案。

纪要记录实际问题、原因、问前证据、选项及推荐理由、实际回答（原话或注明忠实转述）、确认结论、未决问题。不记录模型内部思考，不倾倒整段工具输出。完成时可简短汇总结论，但不能把总结当作缺失的问答证据。

意图必须引用本次纪要；纪要通过 `intent_id` 反向关联。即使访谈未完成也应保持关联。新意图类型尚无法确定时可先分配编号、保存纪要并标注待建立意图链接；不能虚构目标文件已存在。类型明确并创建草稿后立即补引用；最终录入完成必须双向可追溯。

意图移动时纪要不移动；更新当前有效的路径链接和索引，但历史原话或代码块中的旧路径作为历史证据保留，不能无差别全局替换。

### 5.3 旧记录

旧版 `type: interview` 纪要与 `related` 引用仍可读取，不能仅因新模板改变就判定历史答案不存在。首次继续维护旧意图时按需补字段并引用旧纪要，不批量迁移历史、不改旧编号；未明确要求时，不移动旧纪要或将旧意图重建一份。

## 6. 模式交接与权限

启动推进在可写模式下，先核实唯一目标、类型、状态、路径与目标冲突，再记录启动依据并迁入对应实施目录。更新 `status_dir`、日期、有效入出链和沿途 README，核实完整后才继续调研、补访或切换。已在实施则不重复迁移或追加启动记录；迁移不完整时停止后续切换，重试按实际位置修复未完成项。

只读模式不移动或修复文件，可继续原生只读规划。仍在待办或旧进行中时，报告未迁移并将“恢复可写后、业务实施前完成迁移核实”列为前置交付项；已在实施且完整时直接继续，不误报为未启动；有待修复项则如实列入计划。

普通模式的“计划交接”整理目标、范围、约束、验收、已决定事项、代码线索、风险和仍需研究的技术问题。这是规划输入，不是正式实施步骤清单。目录进入实施不等于计划获批，也不授予业务代码写入。

准备充分后调用宿主实际提供的原生计划模式能力。需要用户批准时遵守宿主流程；没有工具、失败、被拒绝或结果无法确认时，提示用户手动切换并停止。存在计划文件、用户说“做个计划”或自设 `plan_mode=true` 都不是已进入模式的证据。已经迁入实施但切换失败或暂停的，意图留在实施。

已经在计划模式时不退出再进入。三个 Skill 都受宿主权限限制：只读模式不能为了纪要改项目文件。新增问答暂留会话或宿主明确允许的计划产物，写清“待归档、未写入项目”，保留恢复材料，不宣称持久化完成。未知写权限时遵守宿主约束，无法确认则停止受限写入。

切换确认后在原生计划模式正式研究并制定计划，包含实施步骤、修改范围、验证与完成标准、风险及必要的迁移安排，按宿主流程交付审批。不为满足纪要持久化而自行退出模式。正式计划保留宿主实际返回的位置；未返回文件路径时不编造。需要归档的纪要和引用列入交付，不能靠请求规划推定已获执行授权。

## 7. 写入与移动安全

- 只改本次意图、纪要、必要索引及相关链接，不改规范、Wiki、记忆或业务代码。意图域里的记录不能自动升级为强制规范。
- 操作前读目标，核实仓库内路径与真实文件类型；拒绝意图/纪要路径中的仓外解析、软链或 junction 重定向，不通过其他路径绕过限制。
- 写前检查密码、令牌、Cookie、私钥、完整连接串和个人敏感信息。只保留安全描述与必要的位置引用，不复述秘密；无法安全表达时阻断相应写入，标注已脱敏的省略，不伪称完整原话。
- 废弃前核实用户授权、真实原因、目标无冲突及引用位置。先保存纪要与决定，再执行普通文件移动，保留编号和历史；不使用强制覆盖、删除、stash、强制 Git 清理或回滚。
- 移动后更新 `status_dir`、日期、必要引用与沿途 README，检查当前有效的入站和出站链接。途中失败时报告已经完成及尚未完成的步骤和实际文件位置；不伪称原子操作，不用强制覆盖完成恢复。
- 同一意图处理完再处理下一条。源文件被外部修改时先重读并合并真实变化，不覆盖用户新内容。
