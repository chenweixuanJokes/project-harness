## 2. 提交与评审

- **提交信息**：跟随仓库已有写法；仓库没有约定时用 `<类型>: <说明>` 一行式（类型 `feat` / `fix` / `refactor` / `docs` / `chore` / `test`），说明写清这一提交做了什么，正文（可选）写为什么。`wip:` 提交只用于第 3 节的隔离与阻断场景，不与正式提交混用。
- **提交粒度**：一个提交对应一个可说明的目的，混合多事的提交先拆分或说明。生成物、锁文件、格式化与业务改动的合并方式按本仓库现状登记：`<填写>`。

## 3. WIP 与 stash

- 禁止 `git stash`。
- 切换分支、进入 / 退出 worktree、合并或删除隔离环境前，若工作区有未提交改动，先提交：

  ```text
  wip: <说明>
  ```

- WIP 不得静默执行。提交前列出 staged、unstaged、untracked 清单，并统一执行“WIP 确认”：先只读检查，列明所在目录、当前分支、完整改动清单与拟用的 `wip: <说明>` 提交信息，用于说明现场与安全筛查结果；随后按下方固定问句模板实际调用问答工具提问；不开放式问“怎么办 / 要包括哪些”。WIP 确认问的是是否采用 `wip:` 提交解决当前这次阻断，不是对文件内容的逐项审批。对用户开口时遵守 [对用户提问](../harness规范/对用户提问规范.md) 的“把问题写成可回答的决定”，说“隔离工作区 / 这次任务的工作目录”，不把内部会话名或脚本参数当问句。用户确认才提交，拒绝、取消或未回答保留改动并暂停。确认后到这次提交实际执行前：分支、HEAD 或拟提交路径/状态集合发生变化（新增、删除或路径状态在 staged / unstaged / untracked 之间转移）时阻断并重新预检、重新确认，不沿用已消费的确认覆盖新变更；同一已展示路径的普通内容修改不需要重新确认（不逐字节比对文件内容）；授权不是长期授权：该提交一经执行授权即消费，该阻断场景结束后再次被未提交改动阻断（包括后续步骤、下一次交付或该工作区再次变脏），按当时的现场重新确认。受确认的 `wip:` 提交在同一个 `enter --apply` / `exit --apply` 调用内由运行时脚本执行：`--wip-message "wip: <说明>"` 携带分支与 HEAD 绑定（enter 使用 `--expect-source-branch`、`--expect-source-head`；exit 使用 `--expect-branch`、`--expect-head`）以及 `--expect-staged`、`--expect-unstaged`、`--expect-untracked` 绑定 dry-run 快照（独立 `wip` 子命令保留给用户直接使用，技能流程不拆成两次调用）。`--apply` 缺任一绑定，或分支、HEAD、拟提交路径/状态集合与 dry-run 不一致时脚本整单拒绝并要求重新预检，防止把提交落到别的分支或沿用旧确认提交新的改动范围；不由 Agent 手写 `git add` / `git commit` 拼装这次提交；提交把 staged、unstaged、untracked 一起收进，ignored 排除，不盲目 `git add -A`，疑似密钥、异常大文件、ignored 文件与未解决的冲突不得为 WIP 收进，脚本整单拒绝、不部分提交，也不得绕过安全门禁。筛查发现无法纳入的非 ignored 变动时，流程在其被用户处置之前保持阻断：即使其中部分路径已另行经授权提交，也不得把该工作区当作干净继续操作；受确认提交完成后脚本只见 clean 工作区。脚本自身不向用户征求授权，脚本无能力证明真实用户确认，人类确认由问答流程在调用 `--apply` 前完成。确认只覆盖这次 `wip:` 提交，不授权普通提交、清理或安全检查豁免。清理前的“能不能删这个目录”仍单独问。
- **固定问句模板**（“WIP 确认”统一使用原文，只替换目录、分支、清单、wip 说明、后续动作五个变量）：

  ```text
  <目录>（分支 <分支>）有未提交改动：<清单>。拟提交 `wip: <wip说明>` 后<后续动作>。是否继续？
  ```

  问答工具的两个选项文案固定为字面“是”“否”，不添加其他预设选项，也不禁用宿主自带的自由输入（如 Other），自由输入按其本意处理：同意才提交，拒绝、取消或未回答停止。“是”授权的是本次组合调用：单次 `--apply` 内由脚本完成受确认的 `wip:` 提交与后续动作（创建隔离工作区或继续交付），技能流程不拆成两次脚本调用。没有可用问答工具或工具故障时，按 [对用户提问](../harness规范/对用户提问规范.md) 的降级规则用可见文字提出同一模板并等待回答。
- **WIP 授权**：进入 / 退出 worktree、切换分支、合并或删除隔离环境前，若需要 `wip:`，必须取得**本次**提交授权。用户同意“做 worktree”不等于同意把未跟踪文件或密钥收进提交。确认针对当前这次阻断：同一已展示路径的普通内容修改不需要重新确认（不逐字节比对文件内容）；分支、HEAD 或拟提交路径/状态集合发生变化（新增、删除或状态转移）时阻断并重新预检、重新确认，不沿用已消费的确认覆盖新变更；授权不是长期授权，新的阻断按当时现场重新确认。
- WIP 默认保留，不自动 squash。是否在合入前整理由本仓库发布约定决定，写在本节，不另起文档。

## 4. Worktree

- 并行任务的隔离目录固定为仓库根下 `.worktrees/<slug>--<hash>/`。`.worktrees/` 是真实目录，不是软链。`slug` 由英文任务分支生成，短 hash 防止大小写、截断与同名冲突；脚本必须校验 Git ref 和目标路径不越出 `.worktrees/`。
- `.worktrees/` 由仓库根 `.gitignore` 的 PH marker `/.worktrees/` 忽略。不要把隔离目录或本机会话状态提交进版本库。
- worktree 是执行环境，不是第二份知识库。约束、Wiki、记忆仍以已入库版本为准；在隔离环境里改这些文件时，随该任务一并提交。
- 进入流程由用户当轮点名 `ph-worktree-enter` 并要求使用时执行，只允许从 clean main worktree 创建一级 linked worktree。源分支和源提交直接取主工作区当前状态，任务分支由代理依据任务语义和本节命名规则确定；用户明确要求创建 worktree 已经构成本次创建授权，正常计划审查通过后直接创建，不再询问这两个分支或是否实际创建。流程记录源目录、源分支、源提交、任务分支、任务路径，以及此刻审核过的验证命令。验证命令会在任务树和合并后的 source 树执行，等同仓库代码，必须经过评审；任务分支后续改写清单不影响本 session。验证命令若改变 staged、tracked 或 untracked 状态，流程必须停止，由用户审查变化。
- 退出流程由用户当轮点名 `ph-worktree-exit` 并要求使用时执行：先跑项目门禁，再安全提交任务改动，合并回进入时记录的源目录与源分支，再次验证。合并采用 Git 默认 fast-forward / merge 策略并显式禁用 autostash。修复或重跑必须覆盖全部 phase 的 dry-run，不能只复验其中一个 phase。进入 worktree 不推导出退出技能的调用授权。
- 退出提交不再按分级默认普通提交：任务树 clean 时跳过提交；任务树有 staged、unstaged 或 untracked 内容（包括只有 staged、只有 tracked unstaged、两者并存、含 untracked）时，先在任务树按第 3 节“WIP 确认”取得本次授权，再以单次 `exit --apply` 携带 `--wip-message` 及第 3 节的完整快照绑定，一次完成受确认的 `wip: <说明>` 提交和交付，不拆成先 wip 再 exit；受确认提交完成后后续交付逻辑只见 clean 工作区。`exit` 兼容接受旧 `--message` 参数但绝不据此提交，只有已确认并完整绑定的 `--wip-message` 才用于此次 WIP；任务树提交一律由受确认的 `wip:` 或用户单独指定的正式提交完成；用户已在本次会话单独明确指定正式提交（范围与消息齐备）时可按指定执行，但调用退出技能不构成 WIP 或提交确认。向用户展示时至少给出 HEAD、当前 branch、index 与 untracked 摘要。合并目标源工作区不干净阻断合并时同样按第 3 节“WIP 确认”处理，WIP 提交做在源工作区。脚本自身不向用户征求授权，脚本无能力证明真实用户确认，其安全分级只在 `--apply` 时兜底拦截不接受的状态，人类确认由调用 `--apply` 前的问答流程完成。存在无法纳入的非 ignored 变动时交付保持阻断，即使其中部分路径已另行经授权提交，也不得把任务树或源工作区当作干净继续。ignored 文件一律阻断清理，并提醒先自行保全；不得加入提交或静默丢弃。不得使用 `--no-verify` 绕过 hooks。
- 交付中断、验证失败或冲突撤销后修复任务分支再次交付时，先核验再交付（`redeliver`，仅适用于 session 处于 `committed` 或 `merge_verify_failed` 且任务分支在其后出现新提交的情况）；对 session、锁与 merge 状态存疑时先用 `doctor` 只读诊断（无 `--apply`，不做任何修复）；确需恢复登记时由 `recover` 显式执行，恢复目标与操作由用户显式指定，不猜测、不自动覆盖现有 session（`archive` 仅适用于已清理或目录不存在且未登记的残留记录，`adopt` 仅适用于 creating 记录且现存登记 worktree、分支与 initialTaskHead 吻合）。现场与登记不符（陌生 merge）或旧版本创建的 session 缺少新增证据字段时保守阻断，不猜测补齐；recover 不能恢复所有旧 merge，先诊断再按结果交用户处置。session 结构向后兼容，1.1.14 起新增字段非必填；迁移不覆盖现有 session。
- **并行开发、串行交付**：多个独立会话允许并行开发，各自在登记的 worktree 或任务分支上推进，互不阻塞。串行的是交付与元数据：对同一源工作区的合并交付（`ph-worktree-exit` 的 merge）与运行时元数据写操作（worktree session 登记、需求状态 mark、归档快照等）同一时刻只执行一条；持有写锁或目标处于合并中时，不同时创建或交付另一条。仅有其他已登记但尚在开发的会话，不阻止创建新的独立任务。worktree 只隔离文件，不隔离外部资源；端口、数据库、锁文件、共享文件与共享索引等外部资源须指定唯一负责人或串行访问。第 2、3 节的提交确认与第 5 节冲突规则不因并行开发而豁免。
- **归档与退出相互独立**：需求归档（`ph-archive`）与退出合并（`ph-worktree-exit`）由用户分别点名，先后顺序均可，互不调用、不互相授权；实现与归档也不自动调用、不授权 enter/exit，点名 enter/exit 不授权实现或归档。在任务分支上先归档时，如实记录「未合入」与快照位置，不宣称源分支已通过验证；合并后引用旧证据前按合并后状态重验受影响项。清理隔离目录前，归档与任务证据必须已保全到该环境之外或受跟踪的交付材料内；指向将被删除目录的链接不是持久证据。
- 合并成功后必须另行征得用户同意，才能普通移除本 session 的 clean linked worktree；对用户问“要不要删掉这个隔离目录”，不要问 session 或脚本参数。默认保留任务分支，不 push、不删分支、不 prune 其它 worktree，也不使用 force。

## 5. 异常处理

异常操作默认停止。下表每一步凡涉及提交、删 worktree、abort-merge、清理 ignored 或改分支，都要**单独授权**，不能用进入 / 退出的原授权顺带覆盖。

| 情况 | 处理 | 额外授权 |
| --- | --- | --- |
| 隔离环境做不下去 | 先按第 3 节 WIP 确认 `wip:`，保留实验分支；用户确认后再删本地 worktree；在对应需求记录（`project-harness/specs/` 下功能目录）写原因 | 本次 WIP；删除该 session 的 worktree |
| 主工作区与 worktree 都有未提交改动 | 两侧分别按第 3 节 WIP 确认 `wip:`，禁止 stash 互搬 | 两侧各自的本次 WIP |
| `.worktrees/` 被误提交 | 从版本库移出并确认 ignore 仍在，不改其它忽略规则 | 从 Git 移出这些路径 |
| 分支名含中文或空格 | 停下来改名，不继续进 worktree | 新分支名 |
| 合并冲突 | 保留 Git 标准 merge 状态；不自动解决。合并冲突态优先于一切 WIP 流程：不问 WIP，冲突问句只属于 `ph-worktree-exit` 自身流程（其交付或恢复中先只读确认冲突态并列明冲突清单，再按下方“冲突固定问句”实际调用问答工具提问；继续用 `ph-worktree-exit continue`，放弃用 `abort-merge`，两者执行前都核对 merge 身份）；另起的 `ph-worktree-enter` 调用遇冲突态只提示用户处于合并状态、等合并完成后再重新调用，不弹冲突问句 | `continue` 需用户明确“已解决并暂存，请继续”；`abort-merge` 由“撤销这次合并”选项授权，仅本次 |
| 验证命令改了工作区 | 停止，列出变化，由用户审查 | 是否保留变化并重跑 |
| ignored 文件挡住清理 | 停止并列路径；用户先保全不可再生成的数据 | 处置 ignored 之后的 cleanup |

- **冲突固定问句**（`ph-worktree-exit` 冲突恢复统一使用原文，只替换目录、任务分支、源分支、清单四个变量）：先只读确认 merge 已真实发生冲突（存在 `MERGE_HEAD` 与未合并条目）并列明冲突清单，随后实际调用问答工具提问；两个选项固定为“保留现场，我解决后继续”“撤销这次合并”，不添加 stash、丢弃、一键选 ours/theirs、Agent 代解决等其他预设选项，也不禁用宿主自带的自由输入（如 Other）。没有可用问答工具或工具故障时，按 [对用户提问](../harness规范/对用户提问规范.md) 的降级规则用可见文字提出同一模板并等待回答。

  ```text
  <目录>中，任务分支<任务分支>合入源分支<源分支>时发生冲突：<清单>。保留现场由你解决后继续，还是撤销这次合并？撤销会取消本次合并中的冲突处理，任务分支提交和隔离目录仍保留。
  ```

  “保留现场，我解决后继续”即停止等待，不立即 continue、不轮询；用户明确说“已解决并暂存，请继续”时，只读核验无未合并条目、核对 merge 身份（session 合并快照 `mergeSourceBranch` / `mergeSourceHead` / `mergeTaskHead` 与现场一致）、session 与任务分支未变、merge 状态吻合，才执行 `continue --apply`，既有具体授权不重问；仅文件无冲突标记、或口头说已解决而没有明确要求继续，都不是继续授权。选择“撤销这次合并”是仅本次 `abort-merge --apply` 的单独授权，执行前说明冲突解决的编辑会被撤销，并只读核对 merge 身份确认撤销的正是本 session 发起的这次合并。取消、跳过或未回答同样停止：不 abort、不做 WIP、不换问法重问。冲突条目涉及业务取舍仍停止交用户；用户明确委托 Agent 解决冲突属单独授权。冲突态优先于第 3 节 WIP 流程：合并前脏工作区才做 WIP 确认，未合并条目不得为 WIP 收进提交；冲突解决后 `continue` 生成合并提交，不是 WIP 提交。新一次 merge 冲突重新提问，不复用旧授权；清理隔离目录仍另行确认。旧版本创建的 session 缺少新增证据字段、无法核对 merge 身份时保守阻断，不猜测补齐：先用 `doctor` 只读诊断，确需恢复登记再由用户显式指定目标与操作（`recover`），recover 不能恢复所有旧 merge，诊断与恢复之外的状态交用户处置。

禁止用 stash、`--force`、`reset --hard`、`--no-verify` 把异常“处理掉”。

## 6. 通知（可选）
