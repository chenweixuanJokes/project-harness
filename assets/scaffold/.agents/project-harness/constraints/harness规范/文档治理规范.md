# 文档治理规范

Last verified: <填写：YYYY-MM-DD>

使用时机：内容分区、索引与宪法导航维护、生效状态定性、资料五字段、文档同步检查、纠正与问答门禁时读本文。

> 管文档怎么放、怎么索引、怎么过期，不管各域的业务事实。业务事实分别写在约束专文、规格正文和资料页。

## 1. 内容分区

| 分区 | 目录 | 效力 |
| --- | --- | --- |
| 约束 | `project-harness/constraints/` | 强制。与其它文档冲突时以约束为准 |
| 项目资料 | `project-harness/documents/` | 现行叙述。过期按 refresh trigger 重验，不把它当规范 |
| 规格 | `project-harness/specs/` | 需求、设计、任务与验证等 SDD 产物及证据，随功能演进 |
| 记忆 | `project-harness/memory/` | 参考记录，不是规范 |
| 历史 | `project-harness/archive/` | 升级前原件、需求归档快照与已沉淀历史，只读追溯 |

`docs/` 属于项目业务文档，PH 不占用、不索引。仓库根 `.specify/`、`docs/意图/`、`docs/约束规范/` 是旧版布局，升级后不再作为活动入口。

## 2. 目录与索引

- `constraints/` 与 `documents/` 内目录名可用中文或英文，同一层保持一致；现有子目录沿用中文命名。
- `constraints/` 内**不设目录索引 README**：每篇文首自写「使用时机：」，导航由宪法逐文件承担；新增约束文用单一主题命名，不回退为汇总文。`documents/` 内每个文档目录仍必须有 `README.md`，只做索引和一句话定位，不复制正文规则，目录下每篇直接文档和每个子目录入口都必须列入；漏索引即失败。
- `constraints/` 中每个约束文件都必须被 `project-harness/constitution.md` 逐文件引用并写明使用时机；新增、移动或移除约束后同步宪法。宪法缺失或引用不全时先修复索引再继续工作。
- 创作模板放在 `runtime/` 模板区；例外：`架构决策/_模板.md` 与各端 `测试用例/_模板.md` 以 `_` 前缀留在 `constraints/`，复制使用、不进宪法导航、不当正文改写。
- 各端 `测试用例/` 目录（`前端测试用例/`、`后端测试用例/`）**只放冒烟用例**，一冒烟用例一文件（命名见 `_模板.md`）；单元等自动化用例留在各端测试目录。宪法导航对这两个目录按目录登记一条，不逐文件展开。
- 新增 / 移动 / 重命名文档后，`documents/` 同步所在目录与各级上级 README；`constraints/` 由 PH init / 升级刷新宪法导航；并检查 `.agents/AGENTS.md` 与其它文档的相对链接。
- 资料（Wiki）非 README、非模板页必须含 owner、status、last_verified、verified_against、refresh_trigger。模板占位允许空值或 `<填写>`，但不得谎报已经核验。 <!-- ph:placeholder-example -->
- 不为脑图或清单上的每个叶子预建空文档。同类约定写进一篇汇总规范，重复结构用模板表达；真正有内容时再拆专文并补索引。
- `.agents/init-report.md` 是初始化补全的实现记录，不属于上述分区；约定见 已安装 `ph-init/references/补全规范.md` 的覆盖报告约定。
- `project-harness/archive/` 保存升级前原件与历史资料，不是现行文档；升级前的被覆盖原文在 `archive/legacy-backup/`，见该目录 README。

### 2.1 固定基础树与架构决策

基础文件和目录保持原路径，不删除、不移动、不重命名；正文随项目演进。新增规范必须有实际内容、单一主题、以“规范.md”结尾并注明使用时机，随后刷新宪法导航。

`架构决策/` 只记录重大架构与技术调整：核心语言、运行时、框架、存储引擎替换，以及公共契约、鉴权机制或核心模块边界变化。测试框架替换、公共模块移除仅在影响全局方案、兼容性或迁移成本时纳入；普通依赖更新和局部实现不写 ADR。记录背景、备选方案、决定和后果，不把草稿当已采纳约束。宪法按目录登记此处，不逐条展开记录。

## 3. 需求与规格

- 需求活动记录在 `project-harness/specs/<编号-主题>/`，路径与编号稳定：目录不随状态或改名搬移，引用不断链。机械状态与指纹在目录内 `ph-feature.json`（经 `ph_sdd.py` 维护）；语义与验收以正文和证据为准，勾选不是通过。
- 完整流程产物为 requirement、design、review、tasks、verify-plan、acceptance、verification；小改动以 `change.md` 替代 requirement 与 design，任务、验证与授权语义不变。各阶段由对应技能承接（`ph-require`、`ph-clarify`、`ph-design`、`ph-design-review`、`ph-tasks`、`ph-verify-plan`、`ph-small-change`、`ph-implement`、`ph-verify`、`ph-archive`，均须当轮点名，不自动串联；`ph-worktree-enter` / `ph-worktree-exit` 同样独立点名，不因实现或归档而被自动调用或授权）。
- 旧 Spec Kit 规格（`spec.md` / `plan.md`）按映射接入：分别作为需求与设计来源，原编号、问答、附件与证据保留；既有勾选不推定通过，按现行门禁实际核验后才可标通过。
- 需求归档（`ph-archive`）把只读快照与索引追加到 `archive/features/`，同时按第 2 节与 4.1 节把已实现事实同步进 `documents/` 受影响页面并维护目录 README 索引与五字段；已验证可复用冒烟用例按 [用例规范](../测试规范/用例规范.md) 第 7 节沉淀。规范（`constraints/`）变更必须已有明确授权，不把实现选择或记忆建议自动升为约束；归档不自动写记忆、不自动调用记忆技能。
- 旧版意图目录（待办 / 实施 / 已废弃 / 访谈纪要）已退役：新需求按上述产物结构承接，过程证据进入 `project-harness/specs/<编号-主题>/`，不再靠目录表达状态。
- 旧意图在升级时完成内容迁移：有效需求与验收目标转入对应需求记录，访谈原话与结论按来源保留在需求附属材料或记忆；仅把原件归档不算完成迁移。
- `archive/` 中的旧意图、旧索引与账本仅供追溯，不当作待办清单或现行需求。

## 4. 生效状态与资料字段

写入任何句子前先定性，四类不得混写在同一条强制句里：

| 状态 | 含义 | 可落点 | 效力 |
| --- | --- | --- | --- |
| 规范 | 本仓库已接受的强制门禁 | `project-harness/constraints/` | 必须遵守；与资料 / 记忆冲突时以约束为准 |
| 事实 | 对照当前代码、锁文件、CI 或已执行命令核实的现行情况 | Wiki、AGENTS 一句话 / 技术栈、开发指南 | 现行叙述；`refresh_trigger` 点燃后先重验 |
| 外部待采纳建议 | 官方指南或评审意见，仓库尚未决定采用 | 意图、ADR 草稿，或专文中明确标注“建议、未生效” | 非强制；不得当成门禁执行 |
| 待核实 | 来源冲突、资料不可达或待执行验证的部分 | 原落点，必须带 `待核实` 与缺口 | 不得宣称已核验或已通过；已有门禁不因本轮未运行而失效 |

原有定制（已填事实、已接受规则、已有 ADR / 意图正文）默认保留。已授权变更需要调整规则时可同步修改，保留依据；冲突无法查清或超出任务范围时，按 [对用户提问](./对用户提问规范.md) 处理。

### 4.1 资料五字段

每篇资料（Wiki）非 README、非模板页顶部 frontmatter 必须含：

| 字段 | 含义 |
| --- | --- |
| `owner` | 谁对过期负责 |
| `status` | `draft` / `active` / `deprecated` |
| `last_verified` | 最近对照事实核对的日期，`YYYY-MM-DD` 或空 |
| `verified_against` | 核对时所依据的提交、标签或路径 |
| `refresh_trigger` | 何种变化发生后本页不得再当现行叙述，必须先重验 |

触发条件已发生、但 `last_verified` 早于该变化时：先重验或标明过期，再引用该页。交付合入前，至少按各页 `refresh_trigger` 扫一遍受影响资料。

补全与同步时的填写纪律：

| 字段 | 填写规则 |
| --- | --- |
| `owner` | 由 CODEOWNERS、现有责任声明或用户明确指定确认；提交作者只能提供线索，不等于当前负责人。无法确认则 `unknown` |
| `status` | `draft` / `active` / `deprecated` 必须与正文一致 |
| `last_verified` | 本次对照事实的日期；未核验保持空，并在正文标明 |
| `verified_against` | 提交、标签或路径；没有 Git 信息就写核过的路径列表 |
| `refresh_trigger` | 沿用页内默认或按真实变化收窄，不留空口号 |

### 4.2 命令标注

```text
<命令>    # 已在本轮执行，通过
<命令>    # 未执行，待核实（抄自 package.json / CI）
```

未执行命令可以登记入口，不能当作门禁已绿；静态读过命令不等于执行成功。

建议默认触发（可按页收窄）：

- 项目概述：目标用户、范围或成功标准变化
- 功能地图：用户可感知功能、路由或模块归属变化
- 开发指南：启动、构建、环境变量或依赖安装命令变化
- 领域页：该域模型、边界或持久化结构变化
- 架构页：模块划分、调用关系或技术选型变化

## 5. 与 AGENTS.md 的关系

`.agents/AGENTS.md` 是精简入口：只保留会话必需的基本要求和读取宪法的指令；长规则写在 `constraints/` 各专文并由宪法引用，不在入口展开第二份。厂商入口是适配层副本，不在那些文件上改治理规则。

## 6. 文档同步检查与修复

由代理按本节在普通会话执行，覆盖 README、配置说明、使用示例与资料现行叙述；本节是规则源。不设定时巡检任务；不因为“该检查了”就自动改资料或造记忆。检查请求默认只读，用户明确要求同步修复才可写文件。

对照范围：

- **当前代码、配置、锁文件、CI、现行约束是全量事实源。** 当前工作区（含未提交改动）是事实；近 7 天提交只提供“可能过期”的变化线索（提交信息、路径、日期），用来优先点名要重验的页，**不**把核验范围限制在这 7 天，也**不**用 7 天无提交推断文档仍然正确。提交标题不能证明实现，找不到提交也不能证明不存在。
- 先读各页 `refresh_trigger`、`last_verified`、`verified_against`。触发已发生且核验日早于该变化，或正文与代码冲突：该页不得再当现行叙述。
- 约束正文纳入已授权变更的同步范围；记录变更依据，不从坏代码倒推规则，不为绕过失败擅自降低门禁（见 §7）。

修复门禁：

1. 只修可直接证实的不一致，保持原文档结构与术语风格；每处修改报告文件与依据，无修改时报告实际核对范围与证据。相关约束可同步更新，在交付说明列出修改的规则与依据。
2. 五个字段必须写真实值；`owner` 未知填 `unknown`，不猜；局部核对不得谎称整页核实。
3. 命令若未执行，保持 `待核实`，见第 4 节。
4. 范围要扩到其它分区或与定制冲突：停止受影响项。
5. `ph-init check` 通过不能代替本流程。

## 7. 纠正

按分区处理。记忆的查询、写入、学习与归档由三个记忆技能执行（`project-harness/memory/README.md` 技能表：回忆查询按用户意图自动触发，写入、学习与归档仅当轮点名才触发）；文档同步检查与修复按 §6 由代理执行，但纠正与同步都不自动升格规则，也不因存在检查规则就自动执行。

| 对象 | 做法 | 禁止 |
| --- | --- | --- |
| 资料 | 对照当前事实改现行正文与五字段；过期原因可留在页内一句 | 不把建议写成已核验事实 |
| 约束 | 在已授权任务范围内随项目更新并留痕；重大架构或技术变化记录 ADR | 不从坏代码或过期资料倒推强制句 |
| 规格 | 新结论追加进对应规格与澄清记录 | 不改历史问答顶替验收结论 |
| 记忆 | 新临时记忆或 structured supersede；archive 原件不改写、不删除 | 不把纠正结果自动升为规范或授权；秘密仍不得入库 |

纠正前先标生效状态（规范 / 事实 / 待采纳建议 / 待核实），定义见第 4 节。待核实内容可以纠正为“仍未知”，不能纠正成未核验的肯定句。

## 8. 问答门禁

回答仓库“现在怎样 / 必须怎样 / 以前记过什么”时：

1. 强制问题只引用 `project-harness/constraints/` 与 `.agents/AGENTS.md`。
2. 现行事实引用经过当前代码复核的资料页；日期新不代表事实仍有效。过期时先只读取证，在回答中说明差异，不能借问答自动执行 §6 的写入修复。
3. 历史回忆由 `ph-memory-ask` 检索 `project-harness/memory/`（按用户意图自动触发）或按归档清单追溯，并标明参考性质。
4. `待采纳建议` 必须说“尚未生效”。`待核实` 必须说缺口，不当答案。
5. 问答本身不写文件、不造记忆、不部署、不通知。用户要求改文档时再按纠正或补全流程授权。
