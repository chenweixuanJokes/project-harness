# 对用户提问

Last verified: 2026-09-15

使用时机：需要用户决定、准备实际发问、使用或记录回答时读本文；内部字段名不代替用户要决定的事。

提问是把尚未解决的决定交给用户，不是展示进度，也不是让用户替代理查资料。本文统一规定何时问、如何实际发问、怎样使用回答。提问前阅读本文，并核对当前流程的授权要求；本文不增加操作权限，也不替代宿主的工具限制和专用审批。

## 何时需要用户决定

先检查用户当前请求、已经给出的回答、项目约束与可核实事实，再判断：

- **能查清的事实，先查不问。** 文件位置、现有实现、已记录的决定等由代理检索；不能把尚未调查说成“需要用户确认”。
- **授权内的普通选择，自主处理。** 有合理默认、影响有限且可逆的实现细节，由代理选定并在必要时说明取舍。存在多个实现方法本身不是提问理由。
- **关键决定或必要授权确有缺口，才问。** 无法从证据解决，且会改变目标、范围、验收、存量兼容或重要外部影响的选择，应交用户决定。所属流程明确要求的审批、安全限制仍须遵守。

已明确回答的同一问题不重复问，已授权的同一操作不追加“现在可以执行吗”。授权不延伸到新的范围或后果：要求调查不等于允许修改，批准实现方案不等于允许发布或清空数据。不要以“采用默认值”为由绕过必要授权。

## 通过正确通道实际提问

1. **先看当前宿主实际提供的能力。** 有能合理表达当前问题的结构化问答工具时，必须实际调用；不猜工具名，不因其他会话用过某工具就假定当前也有。开放问题遇到格式限制时，按下文的明确例外处理，不能仅因偏好文字就认定工具不可用。
2. **一次只提交一个独立决定。** 即使工具支持多个问题，也不把互不依赖的决定塞进同一轮。正文列选项、预告“我会问”、道歉或承诺“下次用工具”，都不能代替调用。
3. **遵守工具格式。** 使用工具自带的自由输入入口，不再添加重复的“其他”选项；选项数量、推荐标记和单选、多选按宿主要求填写。
4. **检查实际结果。** 调用失败不代表问题已成功提交；提交成功不代表已收到回答。只有工具返回的实际回答或用户明确的文字回答，才可作为决定依据。

以下情况使用专用通道：

- **正式计划审批**：使用宿主专用审批能力，不用普通问答代替，也不在审批之外再问一次“是否同意计划”。宿主要求手动操作时，如实说明所需动作。没有专用审批能力时，只按宿主明确允许的替代流程办理；没有允许的替代流程则说明阻断并停止依赖审批的操作，不把普通问答伪装成审批完成。
- **密码、令牌等秘密**：使用已配置的安全采集流程，或让用户直接在目标服务完成登录。不得要求用户在聊天、普通问答或纪要里填写秘密；没有安全通道时停止采集。

**降级必须有实际原因。** 确实没有问答工具，或技术故障经合理检查仍无法恢复时，说明限制，用可见文字提出同等问题并等待回答，不声称已通过工具提问。不为获得工具而擅自切换工作模式。根据结果的具体原因区分故障与拒绝，不仅凭“error”状态判断；权限拒绝、用户取消或跳过，以及无法确认原因的无有效回答，都保留未决状态。没有技术故障证据就不自动降级重问，不换通道重复施压，不解释成同意；仅在用户主动恢复或出现新的必要决定时继续。

## 把问题写成可回答的决定

一个好问题包含三件事：**已经知道什么、现在请用户决定什么、选择会影响什么**。背景只保留判断所需的信息，详细证据可附路径或链接，不把关键决定埋在长篇进度报告末尾。

- 问句直接指向决定，例如“这次改造需要保留已有实例和数据吗？”，而不是“兼容策略怎么闭环？”
- 选项必须回答问句，并说明真正不同的结果。不要用“先看差异再决定”和“先看差异暂不修改”伪装成两个不同选择。
- 有充分依据才推荐，推荐项置首并说明理由。没有依据就平等呈现，不把最省代理工作量的方案包装成对用户最有利。
- 把有重大后果的选择写清楚，不能用“简化处理”代替“删除已有数据”。决定不兼容不自动授权立即执行删除。
- 开放问题就让用户提供真实答案，不编造原因。例如询问放弃原因时，不用“先不放弃”冒充原因选项。工具强制提供选项时，只列有证据支持的真实回答方向，并保留自由输入；无法合理表达时如实说明格式限制，用文字提出开放问题，不虚构选择。
- 优先用直白完整的句子。必要的版本号、路径、API 名称和错误信息可以准确保留；首次出现的陌生术语简短解释。禁止让内部流程字段代替用户需要决定的事情，而不是禁止所有技术词。

## 根据真实回答推进

**已提交问题、收到回答、取得操作授权是三个不同状态。** 不用推荐项、预选值、沉默或代理推断补齐答案；“继续”只有在上下文能唯一确定其含义时才可采用，不能据此推定清空数据、公开发布等重大授权。

- 回答明确且覆盖当前决定时，直接据此继续，不要求用户再确认一次自己的回答。
- 回答只解决部分问题，或与已有关键约束冲突时，先指出具体差异，只追问仍然影响执行的部分。
- 未获得决定时，不执行依赖它的动作。仍在授权范围内、与该决定无关的调查可以继续，但不能以此掩盖未决问题或宣称任务已完成。
- 用户改变目标或撤回请求时，以当前有效请求为准；不机械追问已经失去意义的旧问题。
- 按所属流程保存必要的决定、理由和范围。需要访谈纪要或升级记录时如实写入，区分用户原话与代理解释；普通聊天不强制创建文件。任何记录都不保存秘密。

## 纠正失误与恢复中断

用户指出“没有用工具”“问题问错了”时，先确认该决定是否仍未解决。若仍未解决且用户要求继续原任务，修正问法并**实际提交问题**；不能只回复“明白了”，也不能以修改规范代替本次提问。若用户已经给出答案或要求改做别的事，不重发旧问题。

规则修改和业务澄清分别验收：可以报告“提问规则已更新”，但没有获得答案时不能报告“需求已确认”。中断后复用已有答案，只恢复未解决的决定，不从头重复整轮访谈。

用户指定规则在全局或主项目生效时，核实相应真实约束源和入口，修改授权范围内的源文件；仅改隔离副本不能声称指定作用域已生效。改动仍在任务工作目录时说明实际位置。这不是自动合并、提交或改动其他作用域的授权。

## 边界示例

以下示例说明判断方式，不是要求每个流程都重复询问。工具可用时，问题内容应放进实际工具调用，而不是照抄到普通回复后就停止。

### 存量兼容确实未定

已查明新结构无法直接识别旧实例，尚无数据保留决定：

> 旧实例使用的标识与新结构不同。**这次改造需要保留已有实例和数据吗？** 保留需要兼容或迁移；不保留会让旧实例无法继续使用，实际清理仍需明确授权。

- 保留已有实例和数据（有生产数据证据时可推荐，并说明保护现有使用者）。
- 不要求兼容旧实例（说明仅适用于用户确认无需保留的情形）。

用户已明确“必须保留所有现有数据”时，直接设计兼容方案，不再问一遍是否保留。

### 已授权的操作不重问

用户明确要求创建隔离工作区，正常安全检查通过后直接执行既有创建流程。来源使用主工作区当前分支，任务分支按项目规则确定，不再询问来源、名称或“是否真正创建”。发现未知未提交改动等安全阻断时，只处理具体阻断，不把整个创建授权重新问一遍。

### 问真实原因，不替用户编理由

用户要求放弃需求，而流程要求记录原因且现有信息没有原因：问“这条需求为什么不再做？我会按你的说明记录原因。”不要自行归因为优先级低，也不要让“先不放弃”成为原因选项。

### 故障、拒绝和纠正不是同一件事

- 工具服务故障且无法恢复：说明工具未成功提交，用文字问同一决定，等待答案。
- 用户取消问题：保持未决，不换成文字强迫再选一次。
- 用户说“要用 Ask，继续刚才的问题”：若答案仍缺失且工具可用，实际调用，不以“这次会用”结束。
- 用户说“必须保留数据，另外把提问规则改好”：答案已经明确；按授权改规则，不再重复提问。

## 完成检查

提问前：这真是用户需要决定的事吗？现有证据或授权是否已足够？是否选对通道、只问一个决定、清楚表达后果？

提问后：问题是否实际提交？回答是否真正解决了缺口？下一步是否在授权范围内？若仍未决，是否停止依赖该决定的动作并如实说明？
